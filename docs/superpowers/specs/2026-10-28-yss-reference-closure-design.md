# YSS 初始化引用闭包设计

日期：2026-10-28

状态：已由用户审阅通过（2026-10-28）

范围：`yss-spec-project-template` 与 `yss-cli`，Spec / Backend 两个 Profile

## 背景与目标

当前 CLI 固定模板 4.8.0（提交 `03ee0afcfd2c8b2138981927e4deea8b52bc4c3e`）。静态审计发现，项目入口及技能中既有按条件加载的引用，也有可能缺失的治理入口、已排除的旧政策和不存在的跨端文档。审计不等于真实初始化产物验证。

目标是让每种安装方式在实际启用的能力范围内可找到必需文件，并对不支持或需要治理上下文的条件功能给出准确入口；修复已确认的错误引用，避免把模板维护资产误当成项目资产。已有实例的来源、安装方式、用户文件和治理历史须受到现有同步及事务保护。

## 方案与边界

用户选择方案 A：默认 `skills` 保留普通独立技能能力，正式治理与审计式研究使用 `governed` 安装或已有且可核验的治理仓。选择理由是与当前安装合同、项目身份和既有测试一致，并避免把治理子集误当成完整治理。

考虑过方案 B：将审计式竞品研究的两份模板、校验脚本和全部传递依赖封装到默认 `skills`，使其独立执行。该方案扩大了独立安装及维护范围，不在本次实施。

不复制整个 `.template-source`；不因所有文本路径都匹配而安装整个 `.template-spec`；不恢复已退役角色政策，不改变真实批准、外部动作或现有实例的授权边界。不新增独立研究能力、发布、推送或自动迁移安装方式。

## 引用分类与行为

| 分类 | 处理规则 |
| --- | --- |
| 当前安装入口必需 | 初始化即提供可读资产及入口实际使用的依赖；缺失时不得报告相关能力就绪。 |
| 治理阶段或技能的条件依赖 | 使用现有 Spec `assets ensure` / `skills ensure` 预检及补装；Backend 使用该 Profile 已允许的分发集合。验证目标能力的依赖而非要求所有未来资产立即存在。 |
| 模板维护专用 | 仅模板源使用；项目实例的入口和指引不能要求读取 `.template-source`。 |
| 运行时生成或用户提供 | 明确生成时机、来源或缺失诊断，不作为出厂静态文件。 |
| 可选配置、历史、示例和否定性文字 | 保留明确的适用条件，不把文字出现当成必须安装。历史记录按原政策读取，不改写历史。 |

对条件分支，允许引用实际治理仓的资产，但不得暗示 `skills` 项目根已拥有它们。缺少可信治理上下文时，说明该功能需要已启用治理的仓库或显式转换，不创建伪造的治理身份、批准或记录。入口说明和诊断应遵循现有 CLI 实际能力，不为此设计假造一条新命令。

## 修复范围

### Spec

1. 在真实候选 Bundle / 实例中确认根 `AGENTS.md` 的 `.template-spec/process/agent-entry-policy.md` 引用；若如静态分析所示未安装，将该入口纳入 `governed` common 初始资产，并校验它在当前条件下必需的依赖。确认未安装之前不把静态结论记为测试结果。
2. 修正 `yss-product-lifecycle/SKILL.md` 的维护强度引用：项目治理使用其现行实例政策，`.template-source/process/maintenance-intensity.yaml` 只属于模板维护。检查技能内及实际分发入口的相同边界。
3. 修正 `yss-design-system` 对 `.template-source/design/design-system-sync.yaml` 的更新要求，使之仅适用于模板源；项目内设计系统能力继续使用项目实际资产。脚本在该文件存在时的校验保持原有含义。
4. 审计式竞品研究只在已核验治理上下文使用。其两份模板、`scripts/lib/json-schema.mjs`、`scripts/lib/validation-phase.mjs` 与实际递归依赖必须在支持该分支的治理能力下可用；普通研究不加载该分支。若现有治理分发或补装无法满足，以修正相应治理依赖清单来支持，不把这些文件复制到默认 `skills`。

### Backend

1. 在组合后的 Backend 产物中核对入口政策与 `harness-orchestrator` 对 `digital-human-roles.yaml`、`user-decision-template.yaml` 的引用。按当前编排合同及实际用户决定验证链修正旧角色政策；禁止为消除悬空而恢复退役角色或会签要求。若当前证据链确实需要模板，提供与现行合同一致、可分发的模板；否则改为指向实际权威资产。
2. `frontend-backend-delivery.md` 在固定源码中不存在。核对当前 Backend 职责、交接合同与消费链，将引用改为真实现行事实源；不能仅放宽分发排除。若找不到适用合同，相关跨端能力明确阻断并说明缺失，不凭空补造规则。
3. 对 `plan-migration.md` 等条件引用按实际 Profile 支持范围处理：支持则在条件能力中提供依赖，不支持则明确不支持并修正入口。可选配置及运行时文件不因扫描命中而初始化。
4. 普通 `code-review` 的四项 `.template-spec` 引用仅用于显式正式任务：`issue-tracker.md`、`document-writing.md`、`orchestration-contract.yaml`、`review-report-template.md`。普通审查保持技能内路径；正式审查读取可信治理仓及其实际政策。

### 共享与分发

修改共享技能的 canonical 来源或对应 Backend overlay，并通过现有同步与锁工具生成投影；不手工维护投影副本。Spec `governed` 使用 common、初始阶段和补装闭包；Backend `governed` 初始化使用符合其清单的分发全集。两者均排除 `.template-source`。默认 `skills` 不建立治理身份或安装 `.template-spec`。

## 验收

使用相同候选模板来源构造 Bundle，并核验 Bundle 和实例元数据的 Profile、安装方式与来源，避免误测当前固定的旧版本。至少覆盖：

1. Spec / Backend × `skills` / `governed` 四种临时初始化。`skills` 普通入口及技能内参考可读，不含 `.template-source` 或 `.template-spec`；`governed` 无 `.template-source`，各 Profile 的当前入口必需资产可读。
2. Spec 治理初始入口及其实际必需依赖；对一个实际受影响阶段和技能执行现有 plan/apply 补装后验证对应条件依赖。Backend 检查修正后的入口、用户决定和跨端条件路径。
3. 普通研究不触发审计竞品分支；正式审计研究在可信治理上下文验证两份模板、脚本模块和传递依赖，缺治理上下文时给出准确边界。普通 Backend 审查不依赖治理文件。
4. 必需文件缺失的负向检查能够指出缺失或拒绝相应能力；模板源专用、可选、动态及运行时路径不会被误判为初始化错误。检查范围要基于声明的能力和执行路径，不能把自然语言全路径正则匹配视为完整闭包。
5. 验证已有实例的同步计划和应用保护：保留原安装方式、用户文件与历史；目标模板来源变化通过既有来源和冲突规则处理。禁止以缺文件推断授权、批准或迁移成功。
6. 用现有定向模板检查、必要的轻量 Go 测试、构建与受影响的黑盒验证；记录真实命令、退出码和未覆盖项。候选来源不匹配或测试因旧来源跳过不算通过。测试满足仓库的离线、小夹具及时间限制。

## 来源和执行限制

本地候选优先使用现有 working-tree 来源合同及隔离 Git index，不改写正式固定来源来伪装已发布提交。现有正式来源锁绑定模板 tag；普通模板提交不自动刷新 CLI。正式来源锁及归档摘要仅在模板具有符合既有发行合同的新 tag、且操作获得相应授权时，先预演现有刷新流程，再按工具合同更新和重建。设计批准不授权提交、推送、打 tag 或发布。模板版本、CLI 版本和实例所用来源分别报告。

验证须使用匹配仓库要求的 Go 工具链及绑定候选来源的 Bundle 和 `yss` 二进制。缺少任一输入时只能报告静态分析或局部验证，不宣布初始化验收通过。
