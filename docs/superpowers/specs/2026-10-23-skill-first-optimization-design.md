# 默认直接使用技能：CLI 技术适配设计

本文仅定义 CLI 的技术适配边界。流程行为的唯一设计来源是[模板主设计](../../../../yss-spec-project-template/.template-source/contracts/2026-10-23-skill-first-optimization-design.md)，证据见[固定版本调研](../../research/2026-10-23-matt-skills-131-simplification.md)。用户于 2026-10-24 确认批准两份设计；本次尚未实施程序变更。

## 1. 目标与范围

让普通工程使用独立技能与工程工具时不加载生命周期治理。CLI 继续提供受管分发和正式治理能力，但调用者不必先完成产品阶段手续才能读取技能。现有身份、退出码、JSON envelope、resolve 就绪语义保持兼容。

不新建本地发现 CLI、流程状态库或通用调度器。宿主原生发现足够时直接使用；后续确有只读本地发现需求才新增接口。

## 2. 代码边界

| 当前位置 | 设计变化 | 保持的边界 |
|---|---|---|
| `internal/project/skills_query.go` | 受管 list/details/resolve 继续提供原能力，不再作为普通 Agent 的执行许可证 | ready/missing/blocked、来源与安装校验不改义 |
| `internal/governance/lifecycle/daily.go` | 保留已有 daily/standard 协议兼容；新默认技能路径不调用它 | 已正式绑定任务不隐式降级 |
| `internal/governance/kernel/semantic_core.go` | 工程工具只读取所需目标信息；正式治理显式使用 Authorities | 治理检查失败不伪造通过 |
| `internal/bundle` 与装配工具 | 消费模板给出的普通/正式分发集合与入口 | 固定来源、摘要、事务与覆盖保护 |
| 初始化、同步、迁移命令入口 | 按模板设计区分新建选择和既有实例 | 普通 sync 不改变活动项目治理方式 |
| 帮助、能力声明和冒烟 | 与实际可执行接口同步 | 不提前宣布尚未实现的命令或安装能力 |

加载解耦应贯穿命令前置处理和执行函数。不能只将下层校验变成可选，却仍在命令入口强制初始化治理 Identity。正式治理消费者仍完整调用所需校验；公共文件系统与事务能力继续复用，避免复制一套宽松实现。

## 3. 初始化与安装接口的设计约束

优先在现有初始化/准备入口表达一次安装选择，不创建新的业务 Profile，不要求普通任务每次声明模式。具体参数名和分发字段在主设计审阅后，通过现有命令及版本合同确定；本稿不提供尚不存在的可执行命令。

新建普通项目取得独立技能入口。显式选择正式治理才安装强制治理入口。已有实例沿原受管状态识别，不因新版本默认值变化而改变流程。普通工程无治理 metadata 仍可使用已安装技能；受管安装与升级需要的来源状态由相应工具单独核验。

迁移沿现有 plan/apply 与事务体系进行，不另建迁移状态机。计划绑定当前文件，应用前检查漂移；活跃正式任务先明确处置，历史资产保留。回滚遇到用户后续修改时报告冲突，不重置工作树。

## 4. 实施依赖与验收

模板先明确入口和分发合同；CLI 再实现安装选择、按需加载和迁移；最终刷新固定 Bundle。中间批次可以验证源码行为，但不能声称已发布默认去门禁。来源更新遵循既有生成入口，不能手工修改摘要以制造装配通过。

验收至少覆盖：普通工程不经 Authorities；普通与正式两类初始化；已有正式项目 sync 不转换；活动任务迁移不能绕过处置；plan 后输入漂移；占用目标与损坏来源拒绝；原 resolve 输出兼容。技能的实际推理表现另用任务样例复核，不用 Go 测试代替。

行为变更按根 AGENTS 使用轻量 Go 测试、gofmt、vet 和构建；缺 Bundle 时明确 yss_nobundle 的范围，不能把纯逻辑测试称为完整分发验收。现阶段仅有文档变更，不运行程序测试或生成发行证据。

## 5. 审阅后续

主设计和本技术边界审阅确认后，使用 Superpowers writing-plans 编写到具体文件与测试的实施计划。该计划再确定各批的精确接口、变更顺序和执行方式；本稿不继承昨日另一方案的实施批准。
