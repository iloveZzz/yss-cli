## 1. 目标与已确认决定

将个人工作台的运行数据从整份 `state.json` 转为 SQLite 按记录保存，在保留现有功能的前提下获得事务保存和增量落盘能力。Spec 正文、原型与交互说明继续由项目文件及 Git 管理。

用户已确认：

| 决定 | 本轮约定 |
| --- | --- |
| Q1 改造范围 | 升级存储、按记录更新、事务保护及旧数据迁移；保持页面、命令和检索规则，保留包括隐藏任务在内的全部已有记录；分页、全文搜索另行设计 |
| Q2 旧版兼容 | 升级后使用新版 CLI；不要求旧版读写升级后的最新数据；保留升级前 JSON 备份，恢复该备份不包含升级后的修改 |
| Q3 迁移时机 | 首次启动工作台或执行写入命令时自动迁移；查询不触发迁移；旧工作台运行时提示先退出再重试 |
| Q4 实现路径 | 采用方案 A：保留业务层、内存快照及筛选，将按记录写入和事务集中在存储层 |

本轮不增加团队协作、多设备同步、后台通知、数据库管理页面、导入导出命令或双存储写入模式。不删除旧任务数据，不改变“答复待回写”“延期”“明确确认范围”等业务规则。

失败标准：丢失旧记录；静默回退到旧 JSON；新旧版本各写一份数据；只迁移页面可见字段；查询命令触发迁移或创建数据库；以存储升级名义改变检索、排序或确认规则。

## 2. 当前实现与设计约束

- `src/workbench/store.rs` 集中管理数据目录、锁、校验、JSON 读写与版本冲突。当前 `commit` 对完整状态编码、校验、替换文件并回读；逻辑状态上限为 16 MiB。
- `src/workbench/service.rs`、`registration.rs` 在内存状态副本上应用规则，调用 `Store::commit(expected_revision, next)`。历史记录也属于同一状态。
- `query.rs` 基于完整快照筛选、排序。`content.rs` 重新读取项目产物并验证摘要、问题及确认记录；这些派生状态不是数据库事实。
- `migration.rs` 能将 JSON v1、v2 解码为 v3。`model.rs` 的状态包括项目、Spec、任务、阶段、保存视图、问题答复、内容确认及历史。
- 服务持有数据目录锁及一个 `Store`；CLI 写入可转发给运行中的本地工作台。`session.rs` 当前在读取会话前调用 `read_state`，迁移后必须重新审视这个调用顺序。
- 文件保护使用 `Root`、`RelPath`、文件身份校验及受控替换；SQLite 自己执行文件 I/O，不能因为换了数据库就宣称自然继承这些保护。

迁移保持已有 ID、时间字符串、记录顺序、业务 `revision`、摘要、资源来源信息、个人标记和保存视图内容。旧 JSON 先用既有解码与校验逻辑确认有效，不借迁移清洗数据或重新生成记录。

## 3. Approaches：比较与选择

| 方案 | 实现 | 收益与成本 | 决定 |
| --- | --- | --- | --- |
| A 保留业务层，替换存储层 | 各类记录单独入表，比较前后状态并事务写入差异；读取后重建既有模型 | 改造集中，规则复用；仍有完整快照、全量比较与容量校验的 CPU/内存成本 | 用户已选择 |
| B 按需 SQL 读写 | 服务按操作读取必要数据，查询逐步改成 SQL | 有利于更大数据量；涉及更多服务、来源状态组合与查询行为的回归 | 本轮不采用 |

不采用“将整个状态作为一个 JSON 大字段存入 SQLite”：它仍需整份重写，不能满足按记录保存的目标。DuckDB 的分析查询能力不是本次需求。

## 4. 存储结构与依赖

以下为设计者提出、随 Q5 整体设计确认采用的实现选择：

- 引入 `rusqlite`，启用 `bundled`，将 SQLite 编入 CLI；用户不安装数据库服务。具体版本在实施时按锁定的 Rust 1.99.1 验证并写入 `Cargo.lock`，本轮不安装依赖。
- 使用现有数据目录及 `--data-dir` 语义，主库名为 `workbench.sqlite3`。不放进项目或 Git 工作树。
- 保留既有目录锁；每个工作台进程持有一个写连接，其他 CLI 仍优先通过该工作台提交。不给 SQLite 增加连接池、通用 Repository 框架或第二个数据库后端。
- 写连接使用 `journal_mode=DELETE`、`synchronous=EXTRA`、`foreign_keys=ON`，连接等待锁上限初定 1 秒。成功执行设置后读回核实，不依赖默认值；只读连接不执行持久化 PRAGMA 设置。现有单写入方及短时读取适合先采用回滚日志模式；本轮不启用 WAL，避免引入共享内存文件的管理。

`bundled` 的构建方式见 [rusqlite 官方说明](https://github.com/rusqlite/rusqlite#notes-on-building-rusqlite-and-libsqlite3-sys)。DELETE 模式下 EXTRA 比 FULL 额外同步删除日志所在目录，见 [SQLite synchronous 文档](https://sqlite.org/pragma.html#pragma_synchronous)。这些是选型依据，不是本项目已经完成构建或断电验证的证据。

### 4.1 表与记录表示

本轮采用“每条记录一行，主键和必要关联列显式保存，完整业务记录作为 JSON payload”的形式。它避免为每个字段重复维护转换代码，也允许只更新发生变化的记录；查询仍使用原有 Rust 模型。

| 表 | 主键/定位字段 | 保存内容 |
| --- | --- | --- |
| `workbench_meta` | 单行固定键 | `database_id`、业务模型版本 3、业务 `revision`、迁移来源摘要与初始 revision |
| `projects` | `id` | 顺序与完整 `ProjectRecord` |
| `specs` | `id`，关联 `project_id` | 顺序与完整 `SpecRecord`，含显式/推断资源及来源目标 |
| `tasks` | `id`，关联 `spec_id` | 顺序与完整旧任务记录，保持隐藏数据可恢复 |
| `stage_records` | `(spec_id, stage)` | 顺序与完整阶段记录 |
| `saved_views` | `id` | 顺序与完整视图、筛选、布局和分组配置 |
| `question_responses` | `id`，关联 `spec_id` | 顺序与完整答复/延期记录，含时区偏移、摘要及影响范围 |
| `confirmations` | `id`，关联 `spec_id` | 顺序与确认范围、产物摘要、时间 |
| `history` | 原数组位置 `position` | 完整 `ChangeEvent`，包括可空关联及任意 JSON before/after 值 |

约束：

1. 各表用显式 `position` 恢复数组顺序，不依赖 SQLite 自然顺序。普通表以业务主键比较差异；删除或顺序变化可更新位置列，无需重写未变 payload。
2. `history` 原校验没有要求事件 ID 唯一或关联目标仍存在，因此不新增这些约束。按数组位置保存，避免迁移时合并或拒绝原来可读取的历史；常规追加只插入新位置。
3. 仅对当前校验已保证存在的关系建立外键，采用不级联删除的约束。保存视图中的筛选 ID、历史中的旧关联不强制外键，不清理悬空筛选。
4. 显式主键/关联列必须与 payload 一致，加载时核对；复用既有全局 ID、路径别名、状态与业务输入校验。JSON payload 使用现有序列化语义，不经过浮点数转换处理历史中的任意 JSON 值。
5. 只建立主键、必要关联索引。检索仍在内存，不预建全文或大量筛选索引，不把待确认状态、原型文件内容和来源健康状态存为第二份权威数据。
6. SQLite 结构版本使用 `PRAGMA user_version=1`，应用标识使用固定 `application_id=0x59535357`（YSSW）。业务模型 `schemaVersion=3`、业务 revision 与数据库结构版本分别管理；未知结构版本拒绝读写。打开时检查预期表、列及关联结构，不执行库内未知视图或触发器。

## 5. 运行时读写

### 5.1 写入事务

保留 `Store::state()` 与 `commit(expected_revision, next)` 的业务边界。`Store` 改为持有目录锁、数据库连接、内存状态、文件身份及结果不确定标记。

一次提交按以下顺序执行：

1. 检查结果不确定标记、目录/数据库身份、调用方 revision 与内存 revision；复用现有业务校验及容量校验。
2. 比较各集合的主键、完整记录和位置，得到新增、更新与删除。真正无变化时保留 revision，不新增历史。
3. 开启 `BEGIN IMMEDIATE`；从数据库读取并核对 `database_id` 和 revision，检查当前连接的外部更改标记；不允许用旧内存快照覆盖另一个连接的提交。
4. 先删除必要的子记录，再更新/插入父子记录；历史差异、答复、确认及其他业务记录在同一事务内完成。禁止 `INSERT OR REPLACE` 隐含删除造成关联丢失，使用明确的更新/插入。
5. 用带旧 revision 条件的更新将 revision 增加一次，确认仅影响一行；复用现有安全整数上限。失败则回滚整个事务。
6. 仅在 COMMIT 成功且提交后的身份与 revision 核验完成后，替换内存状态并返回成功。提交结果或后续校验无法确定时，保留 `uncertain` 行为：停止接受写入，返回 `RecoveryRequired`，提示重启核实，不自动重放用户操作。

使用同一连接的 `PRAGMA data_version` 辅助识别外部 SQLite 提交；它不是业务 revision，也不能跨连接比较。检测到外部改动时拒绝继续使用旧内存快照，要求重新打开；不支持用户直接用数据库工具编辑运行中的库。[SQLite data_version 说明](https://sqlite.org/pragma.html#pragma_data_version)

### 5.2 查询与一致快照

- `snapshot`、`query`、`lifecycle`、`request` 等读取入口继续只读。不存在数据目录时返回原来的空状态，不创建目录、锁文件、数据库或迁移标记。
- 只有旧 JSON 时，继续走 v1/v2/v3 解码并在内存处理，不保存升级结果。
- SQLite 已启用时，使用显式 READ_ONLY 连接，在一个读事务内读取元信息和全部记录；不能让各张表来自不同业务 revision。
- 连接使用原生只读打开标志，不只依靠 `PRAGMA query_only`；不使用 `immutable=1` 绕过运行中数据库的锁与变化检查。[SQLite query_only 说明](https://sqlite.org/pragma.html#pragma_query_only)
- 完成有界读取后重建 `WorkbenchState` 并复用既有校验，再交给 `snapshot`、`query`、`content` 等逻辑。
- 遇到需要回滚热日志的异常库，查询不升级为写连接、不删除日志，返回恢复提示；用户启动新版工作台，由受锁保护的写连接完成 SQLite 恢复。正常并发查询发生锁等待时，超时明确返回忙碌，不回退 JSON。[SQLite 热日志恢复说明](https://sqlite.org/lockingv3.html#dealing_with_hot_journals)

### 5.3 容量边界

本轮保留原有逻辑状态 16 MiB、结构深度/节点数量及接口响应限制。SQLite 文件大小不等于逻辑 JSON 大小，不能用 16 MiB 直接限制物理数据库文件。

写入前仍允许为容量校验临时编码整个状态；数据库只写差异。读取时限制单行 payload 与累计读取大小，重建后复用现有 codec 限制，避免损坏数据库造成无界分配。此设计降低整文件落盘成本，但不消除全量编码、快照和比较成本，也不承诺容量或检索速度提高。

若旧 JSON 原始大小符合限制，但升级到 v3 的规范表示超出当前容量，应在切换标记之前明确拒绝迁移并保留原状态；不得删除记录以迁就限制。容量扩展属于后续独立设计。

## 6. 自动迁移与旧版保护

### 6.1 文件角色

- `workbench.sqlite3`：迁移完成后的唯一运行数据源。
- `state.v{原版本}-backup-{sha256}.json`：原 JSON 的逐字节备份，沿用既有按摘要命名与不覆盖策略；迁移不修改这份备份。
- `state.json`：切换时替换为小型存储标记，不保留一份可继续写入的旧状态。
- `workbench-migrate-{database_id}.sqlite3`：本次迁移的临时数据库，名称只由程序生成，完成前不对业务开放。

标记固定声明 `schemaVersion=0`、`storage="sqlite"`、`markerVersion=1`、`phase`、数据库名称及 `database_id`；迁移阶段还保存临时库名、旧备份名/摘要和初始 revision。新空目录的来源类型明确为 empty、备份为空；旧目录来源类型为 legacy-json，必须包含备份摘要。所有名称须是允许的本目录单文件名，不接受任意路径。未知 markerVersion 拒绝处理。

旧 JSON 解码器仅支持 1/2/3，遇到标记明确报不支持版本。旧 CLI 的会话转发前也会读取旧状态，因此可在转发前被阻止。该保护须用实际旧版二进制验证，不能只根据源码推断宣布兼容验证完成。

### 6.2 迁移过程

1. 获取现有数据目录锁。旧/新工作台占用锁时不迁移，不停止对方进程，提示退出已有工作台后重试。
2. 确认目录只有可解释的旧状态：若存在未被合法标记引用的正式 SQLite 库，不猜测、不覆盖。读取并校验旧 JSON，记录文件身份与摘要；无旧状态则使用默认空状态。
3. 有旧 JSON 时先保存并回读验证逐字节备份。失败到此停止，原 JSON 不变。
4. 在独占新建的临时库中，用一个事务创建表和导入全部记录；数据库元信息绑定本次 `database_id`、来源摘要与初始 revision。关闭后验证数据库完整性、外键及重建状态与解码后的原状态逐项相等；不新增业务事件或递增 revision。
5. 再次确认旧 JSON/缺失状态与开始时一致，使用既有受控原子替换将 `state.json` 写为 `phase="preparing"` 标记。写入前临时库和备份必须已关闭并可靠保存。此刻起旧版不再读取或写入此目录。
6. 将已验证、关闭的临时库按“不覆盖已有文件”方式发布为 `workbench.sqlite3`，同步必要目录，再将标记受控替换为 `phase="active"`。两个文件无法作为一个普通文件事务提交，因此必须保留此中间状态。
7. 核对 active 标记、数据库 ID、revision 和目录身份后，才允许工作台开始提供服务或继续本次业务写入。业务写入失败不会撤销已经完成的存储迁移。

新建空目录也经过临时库及标记流程，防止旧 CLI 将缺失的 `state.json` 当成新工作台并创建第二份数据。

### 6.3 中断处理

| 磁盘状态 | 只读入口 | 启动/写入入口 |
| --- | --- | --- |
| 仅旧 JSON；无正式库 | 读取旧 JSON | 持锁后迁移 |
| preparing 标记，只有匹配临时库 | 返回“迁移未完成，请启动新版工作台” | 校验标记、备份及库身份/初始数据后继续发布 |
| preparing 标记，只有匹配正式库 | 同上 | 校验仍为本次迁移的初始库后完成 active 标记 |
| active 标记与匹配正式库 | 只读 SQLite | 打开 SQLite，正常执行 |
| preparing 两库同时存在、两库都缺失或身份不匹配 | 返回 `RecoveryRequired` | 停止自动处理并列出保留文件，不能选一份猜测恢复 |
| active 标记但库缺失/损坏/版本未知 | 明确报错 | 明确报错；不从旧备份静默恢复 |
| 正式库存在，但标记缺失、变回旧 JSON 或指向别的库 | 明确报错 | 停止并提示存储冲突，不能创建或重迁移 |

恢复仅处理标记明确绑定的临时库或已发布初始库；检查来源摘要、初始 revision、完整记录与备份一致，empty 来源则与默认空状态比较。不会修改或删除无法证明归属的文件。切换标记前遗留的未引用临时文件不作为数据源，也不阻止重新从旧 JSON 开始；不通过扫描文件名猜测其归属。切换标记之前的失败保留原 JSON；切换标记之后的失败可能需要续迁，但原始内容仍在已校验备份中。错误须区分这两个情况。

### 6.4 CLI 与会话入口

现有 `register`/`respond` 先尝试转发会话，再打开本地 Store。实施时增加无副作用的存储状态识别：

- legacy/empty/preparing：进入持锁的 Store 打开/恢复路径，不把请求转发给旧工作台；旧进程仍持锁则提示先退出。
- active：保留既有会话认证、地址校验和转发规则；没有可用会话才尝试本地持锁写入。
- invalid：保留数据并返回明确错误。

将 `session.rs` 的目录/会话安全校验与完整状态读取解耦，防止尚未完成迁移或存在热日志时，CLI 在获得写锁和执行恢复之前就被 `read_state` 拦住。保留原有网络结果不确定时不重复提交的处理；无需新增公开命令或修改会话令牌边界。

### 6.5 用户主动退回旧版

文档说明停掉工作台并完整保留当前 SQLite 数据目录后，可将升级前 JSON 备份复制到一个新的、位于项目之外的数据目录，使用旧 CLI 的既有 `--data-dir` 打开。该目录只代表升级前状态。

不在原目录自动反向迁移，不让旧版覆盖现用数据库；不承诺升级后的修改可被旧版读取。出现迁移异常时优先恢复迁移流程，不把回退备份作为默认修复。

## 7. 文件保护与错误处理

继续沿用绝对路径、Git/登记项目隔离、`Root::revalidate`、目录锁、私有状态文件和会话保护。SQLite 打开采用明确标志与受控普通文件路径，不启用 URI 路径解释、扩展加载或来自项目文件的 SQL。

主库/临时库采用独占预创建并核对身份，POSIX 下为 0600；标记与备份同样为 0600。SQLite 主文件启用 `SQLITE_OPEN_NOFOLLOW`，并检查父目录及日志等伴随路径，拒绝符号链接、非普通对象和不符合既有边界的路径。打开前后及提交边界重新核对目录、锁和主文件身份。Windows 继续按现有句柄/路径保护执行，不将 POSIX mode 当作 Windows ACL 验证。[rusqlite OpenFlags](https://docs.rs/rusqlite/latest/rusqlite/struct.OpenFlags.html#associatedconstant.SQLITE_OPEN_NOFOLLOW)

数据库原地写入会改变文件内容，不能继续把“内容摘要变化”当作文件被替换；身份核验应使用不读取整库的受控元数据能力。若现有 fs 接口不足，仅增加所需的小型身份检查，不建立自定义 SQLite VFS。原生 SQLite 对主库与伴随文件的行为需要实际验证，不能把 NOFOLLOW 当作所有路径竞态都已解决的证明；若验证发现会写出数据目录，须修正方案后才能交付。

复用错误类型：锁占用/数据库忙为 `Locked`，revision 冲突为 `ConcurrentChange`，未知格式为 `UnsupportedFormat`，路径不安全为 `UnsafePath`，提交结果不确定、迁移无法续接或需写入恢复为 `RecoveryRequired`。磁盘满等保留 `Io` 及可理解的原因。SQL 错误详情不回显完整 payload、问题答复或会话凭据。

## 9. 实施时的必要验证

按仓库约定使用临时材料验证，不新增持久测试套件或检查流程。下列是本次高风险存储改造的验收内容，当前尚未执行：

1. JSON v1/v2/v3 与新空目录：迁移前后解码状态相等，所有集合、顺序、任意 JSON 值、ID、摘要和 revision 保持；重复打开不再次导入。
2. 覆盖实际数据的边界样例：隐藏任务、多个阶段、停用记录、已保存视图、延期条件与日期/时区、确认范围、重复/旧关联的历史事件。
3. 修改一条记录时，确认 SQL 只更新相应记录及必要顺序/历史/meta；失败注入后记录与 revision 一起回滚。冲突请求不产生部分变更。
4. 在备份、临时库提交、preparing 标记、库发布、active 标记各边界中断并重启，结果符合状态表；身份不匹配和磁盘满不能静默覆盖。
5. 所有纯查询入口在空、旧 JSON、active、preparing、未知格式及需热日志恢复状态下保持只读；对比文件内容、存在性和写入活动，不以读取访问时间变化判断写入。
6. 旧工作台持锁时迁移被拒绝；旧版二进制在迁移后启动、查询、注册和答复均不能写旧 JSON 或误转发；同目录不同新 CLI 仍遵守原有会话及 revision 规则。
7. 对比迁移前后 snapshot、筛选、排序、来源异常、问题回写状态与确认判断，排除随存储变化引入的业务语义改变。
8. 路径/主库/日志的符号链接、替换、权限及未知 DB ID 检查；只读与写连接混合运行时的一致快照、短时锁等待和热日志恢复。
9. 使用现有锁定工具链构建，核实 macOS 和 Windows 包没有用户侧 SQLite 动态库安装要求；分别记录实际构建与实际运行的平台，不将其中之一外推另一平台。
