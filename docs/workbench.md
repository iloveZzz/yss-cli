# 个人 Spec 工作台

当前工作树提供本机多项目的 Spec 阅读与状态核实、自动生命周期汇总和确认、个人标记、工程维护、Pi Agent 原工程运行和历史成果接收入口。目标、证据、人工更正、确认记录、问题答复、草稿及执行记录保存在独立数据目录。工程维护和成果接收按所选目标执行文件写入。已安装版本须核对实际程序、帮助与 Bundle。

```text
yss workbench
yss workbench --no-open --port 0
yss workbench snapshot --json
yss workbench query --entity spec --stage verification --json
yss workbench spec-status --spec-id <SpecID> --json
yss workbench lifecycle-status --spec-id <SpecID> --json
yss workbench recommend-status --spec-id <SpecID> --json
yss workbench lifecycle --spec <SpecID> --json
yss workbench --data-dir /absolute/personal-data
```

默认只监听 `127.0.0.1`，端口由系统分配，打开带临时会话的浏览器链接。无法自动打开时从终端复制完整链接。会话令牌在 URL fragment 中传递，页面读取后清理 URL，并保存于当前浏览器标签页会话；每次服务重启令牌更换。不要把完整启动链接分享给其他人。关闭浏览器后服务与活动作业继续运行，重新打开同一启动链接可查看执行记录。按 Ctrl-C 或退出 CLI 会停止服务并中断活动作业，重新启动后从“执行记录”核对结果及可续接状态。

`workbench` 持续服务不接受 `--json`；`workbench snapshot --json` 使用现有 `yss.output` 信封，command 为 `workbench.snapshot`。快照只读，不创建缺失的数据目录。

## 使用

1. 项目页登记本机绝对目录。路径别名合并为同一个项目，不同 Git worktree 分开登记。数据目录不能在 Git 工作树或登记项目内。
2. 工作台服务启动时扫描已登记且启用的本机项目，新登记项目也会扫描。优先扫描 `docs/spec`、`docs/specs`、`specs`、`.work`，不存在常用目录才从项目根扫描。自动纳管可读的 `spec.md`、`*-spec.md` 或在文档开头（可在主标题后）声明有效 `yss-spec` 元数据的主规格。普通 Markdown 附件不单独纳管；非标准文档可指定目录或相对路径手工关联。自动扫描不恢复停用记录、不修改项目文件。
3. Spec 详情顶部展示有效进度、活跃阶段、局部阻塞及下一步。先设置本次目标、适用阶段、验收引用和参与工程，再由原 Agent 或终端上报成果。个人标记继续单独维护，正文、安全预览、文件时间和可访问性独立展示。
4. “Spec”页通过搜索、项目、阶段、状态与启用范围筛选记录；多选条件内是 OR，条件间是 AND。已选条件显示为可移除标签，列表和看板共用结果，默认隐藏已完成与已取消；显式选择终态会显示相应记录。看板按状态或阶段分组，支持桌面拖动及键盘／触屏“移动到…”菜单；不支持列内排序。每列和列表先显示 50 项，可继续展开。
5. 项目移动后编辑根目录；主文件改名后编辑 Spec 相对路径。ID、历史和个人标记保留。停用不删除，可在显示停用记录后恢复。
6. 生命周期展示调研、分析、规格、原型、交接、实施、验证、交付八阶段，按阶段展开来源、版本、实际成果及检查凭证。执行进度与待核实、待同步、需复核分别表达。旧个人阶段记录可在历史区域查看。
7. 保存视图记录当前查询、布局及分组。临时更改不自动更新收藏，通过“管理视图”更新或移除当前视图；移除只删除查询偏好。浏览器只展示 Spec 视图，已有任务视图仍保留在数据中。工作台首页展示进行中与阻塞 Spec、来源异常、内容待办提醒和活动作业。

项目页“选择当前未关联项”只选择本次发现结果，默认仍不勾选。部分扫描结果会提示限制，启动扫描也会在终端汇报。全局与项目页显示已纳管、已关闭和停用数量；“全部记录”可找回关闭和停用对象，不代表磁盘全部文件或外部平台中的事项。

对同名目录中的 `<key>-spec.md`，未明确关联交互说明或原型时，会发现同目录的 `<key>-interaction.md` 和 `prototypes/<key>/dist/index.html`（或静态 `index.html`）。有自身 Spec 元数据的交互文档不会被推断为附件。已关联原型源码 `index.html` 时，如同目录下已有可预览的 `dist/index.html`，工作台使用后者，不改写 Spec，也不执行构建；仅有源码时提示先构建。预览、版本确认、差异与 Pi 成果使用同一解析规则。

详情可切换渲染预览与原始 Markdown；浏览器搜索同时匹配项目名称、Spec 标题、来源路径、下一步、阻塞和备注。Markdown 仅支持 UTF-8，单文件 2 MiB，不执行 HTML、不加载图片。标记为 mermaid 的代码块可渲染为图表，采用 strict 安全模式，失败时保留源码并显示语法检查提示。HTTP(S) 外部链接不探测；项目内相对 Markdown 链接和关联交互文档可阅读。文档接口允许已授权项目内用户主动打开的 Markdown，仍拒绝绝对路径、越界、链接和子模块。关联内容预览窗口默认最大化，可还原为居中窗口并再次最大化。已构建的本地 HTML 原型在独立本地端口预览，原型预览服务直接提供已构建文件；预览隔离于工作台会话和 API，拒绝越界、链接及源码入口。目录扫描最多处理 10,000 个候选目录项，深度 16；遇到超限或无法访问时提示结果不完整。忽略安装/依赖/构建目录，不穿越 symlink、嵌套 Git 工作树或子模块。根身份及 Git 边界检查独立于候选枚举预算。

## 自动生命周期跟进

本次目标绑定主 Spec、规格摘要、适用阶段、多个参与工程与交付目标。同一目标可采用本地实现、合并或环境验证条件。普通 Codex／终端工作使用 `workbench progress` 写入相同身份；具体输入见随模板分发的 `.template-spec/agents/workbench-progress.md`。运行 `yss workbench progress --help` 核实当前程序能力。

`progress set-goal`、`progress report` 和 `progress reconcile` 核对当前目标和证据，达到条件时自动记录规格、验证及最终目标确认。自动记录标为「YSS 自动核实」。当前仍适用的人工退回由工作台保留，也可用 `workbench lifecycle-confirm` 记录用户另行作出的明确决定。业务问题答复、主 Spec 内容确认和 Pi 编辑授权继续走各自入口。

`yss workbench lifecycle-status --spec-id <SpecID> --json` 只读查看当前目标、阶段证据及确认。`recommend-status` 只读提供 `recommendedStatus`、`recommendedStage` 和 `recommendedAction`。当 `recommendedAction` 为 `autoConfirm` 时，可运行 `yss workbench lifecycle-auto-confirm --spec-id <SpecID> --request-id <本次操作的稳定ID> --json`，对已经保存的证据补记确认。所有命令沿用原数据目录。具体参数见 [命令参考](cli-help.md#自动核实并确认生命周期)。

阶段同时记录执行进度与证据适用性。存在进行中工程时整体显示进行中，并保留其他工程的局部阻塞。其余存在明确阻塞时显示受阻。Backend、Frontend 和联调按实际工程分别展开，验证报告核对实际参与版本组合。工作台在当前目标的有效证据齐备后确认最终结果。证据缺失、过期或检查失败时，查看阶段诊断并补齐所需证据。目标结果也可在「目标结果确认」入口查看。

交付确认记录目标版本、当时的范围和凭证。自动确认随当前证据失效，旧记录仍可在历史中查看。已有明确人工验收的目标保留其历史完成状态，候选内容和材料影响另有提醒。登记新一轮目标后显示该轮进展。同一目标版本的明确退回优先于自动确认。

规格与相关代码变化会触发适用性核实。局部报告通过 `progress observe-inputs` 在执行检查前采集实际输入，通过 `inputPaths` 随凭证上报。工作台按文件集合、字节和文件模式复核。范围内的输入一致时可沿用局部凭证和对应确认。范围证据缺失时显示待核实，真实的联调、合并和环境验证仍核对实际版本组合。首次发现文件只记产物来源，缺失的历史起止时间继续显示未知。

自动看板的拖动与“移动到”打开人工更正，填写原因并绑定当前目标版本。人工更正优先，冲突证据持续展示，可选择恢复自动判定。目标换版后重新核实原更正。确认记录绑定目标版本、阶段范围及适用证据。旧页面保存冲突时保留输入，重新核对后提交。

新界面默认有效进度。旧查询及未携带 `progressBasis` 的保存视图继续按个人标记解释，切换有效进度后可另存或更新视图。待确认、待核实、待同步、需复核和证据冲突可独立筛选。个人关注、备注及旧记录在个人标记区域继续查看。

工作台和规格管理先显示登记信息，服务在后台核对材料、工程版本和检查输入。同一服务的页面共享最近一次核验结果和约五秒一次的来源检查。服务重启或核验失败时，页面显示核验状态，已有结果保留核验时间。筛选与翻页沿用同一查询版本，遇到变化从首批重新读取。确认、接收及进度写入仍检查当前来源和版本。

活跃 Spec 已明确绑定的远端关联每六十秒刷新，同一关联通过原作业锁串行读取。瞬态失败指数退避至十分钟，认证异常等待核实连接后手工刷新。PR／MR、CI 的状态补充已关联工程及阶段角色的证据，完成条件依据本次目标及实际版本。

工作台从已保存的作业、冻结成果及按工程保存的接收回执显示本轮活动。实际进度由成果、检查报告和适用的确认记录汇总。续接沿原会话开展，新一轮默认采用当前目标的主阶段，也可明确选择当前目标中的适用阶段。已启动轮次保留原绑定。

## 工程维护与产品 Home

工程详情页与“设置”页提供“工程维护”。先读取工程状态，再选择诊断、技能清单或补装、init、attach、sync、DDD/MVC/Frontend 脚手架、事务恢复或工具升级。表单使用当前 Bundle 的真实技能和配方，生成工程时 root 填输出父目录，升级时填独立工具目录。

1. 填写目标绝对路径与本次参数，选择“查看执行内容”。
2. 核对文件变化、保留内容、配方来源和诊断，再选择“执行此操作”。
3. 在“执行记录”查看日志、结果或停止该作业。执行前会重新核对根身份、Bundle、参数和文件指纹，变化后需重新预览。
4. 遇到 `recoveryRequired` 或 `cleanup pending` 时，按实际项目或工具根执行 recover。升级结果分别显示当前进程与磁盘构建，核对结果后可在“设置”重启工作台。

“项目”页的“产品 Home”可导入现有 `REPOSITORIES.md` 或等价 README 表格。读取地图后核对职责、Git 身份与仓内子路径，逐行绑定本机工程绝对路径。非标准表头可指定字段映射，识别有歧义时编辑并采用人工核对的条目，再保存绑定。成功绑定会复用或登记对应本地工程，可继续在 Spec 的“运行 Pi Agent”中选择参与工程。

项目原地图继续维护仓库关系，工作台保存本机绑定缓存和来源摘要。地图变化后重新导入核对。Issue tracker 从各工程的 `.template-spec/agents/issue-tracker.md` 读取。工程、Spec 和设置中的“研发关联”独立保存于个人数据，可关联 GitHub/GitLab Issue、PR/MR 或 CI 运行 ID，通过本机已认证的 gh/glab 固定 GET 读取状态，支持自建实例地址、协议与端口。读取失败时保留上次成功结果及时间。

“本机设置 → 本机与诊断 → 本机工具”显示 Git、gh、glab 的探测路径与版本，并分别报告 Pi 基础作业和离线命令就绪状态。桌面版可从这里选择单项或批量安装，macOS 使用现有 Homebrew，Windows 使用现有 WinGet。安装后重新检测，以工作台服务实际看到的路径和版本为准。桌面自有服务在活动及排队作业允许时刷新，外部服务由用户自行刷新。浏览器工作台提供原有诊断与安装指引。远端状态读取使用对应平台 CLI 的现有认证。

桌面版“检查官方版本”读取 Git、GitHub CLI、GitLab CLI 和 Pi 的官方稳定版本，并提供官方发行页及适用的安装包。gh 和 glab 可选原安装渠道或官方发行包，单项和批量安装共用这一选择。Homebrew 或 WinGet 尚未提供目标版本时，可从工具行或操作结果中改用官方包。工作台校验官方摘要和实际可执行版本，将工具安装到当前用户的应用管理目录。桌面自有服务会优先使用该版本，终端继续使用原来的工具路径。Git 使用 Homebrew、WinGet 或系统提供的版本，macOS 可从 Git 官方安装指引查看其他途径。

更新确认页列出当前执行路径、版本、目标版本、来源和前置项。版本或路径变化后需重新检查。桌面自有服务保存草稿、确认无活动和排队作业并安全停止后，才切换工具。服务重新连接后，以实际检测到的版本确认结果。外部工作台通过原渠道更新和刷新。

桌面首次安装 Pi 使用 `@earendil-works/pi-coding-agent@1.6.1`。更新受管 Pi 或把 PATH 中的旧 Pi 切换到桌面自有服务的受管新版时，工作台使用官方 npm 稳定版中的精确版本并验证 Node 要求和 RPC。仅验证通过时才切换到新的私有目录，旧版本、默认 Node、模型和登录配置继续保留。显式设置 `YSS_PI_EXECUTABLE` 时继续使用指定程序。新主版本需等待工作台适配。

## 在工作台运行 Pi Agent

当前源码在 macOS ARM64 与 Windows x64 上查找本机 Pi 1.5.2、1.6.0 或 1.6.1。Pi 从工作台启动时的 PATH 发现，也可用 `YSS_PI_EXECUTABLE` 指定绝对路径。桌面受管 Pi 使用经过版本检测的 Node 和固定包入口。工作台默认使用当前账户主目录的 `.pi/agent`，也可在启动工作台时用 `PI_CODING_AGENT_DIR` 指定其他本机配置目录。检测、测试连接和运行前会读取该目录中的当前 Pi 配置。工作台使用主工程 `.agents/skills`、参与工程的规则以及内置受控工具。Windows 基础作业在运行时检查私有目录、管道和 Pi 模型配置，可在检查通过后分析 Spec、按本轮授权读写、等待答复、续接和取消。

在 Spec 的“运行 Pi Agent”中点击输入区右下角的模型名，可按供应商筛选或搜索模型。工作台打开选择器时从本机 Pi 离线读取当前候选，并展示所选模型实际支持的推理级别。新会话可切回 Pi 默认模型。已配置 `enabledModels` 时，Pi 按该设置确定启动模型。未配置启动范围时，完整保存的默认模型必须可用，只填写一个默认字段时由 Pi 自动选择。已有会话默认沿用最近使用的模型，在下一次发送前可明确切换，并保留会话历史及参与工程。有效的推理级别随同一模型续接。模型与推理级别均按轮使用，Pi 的全局默认配置由用户管理。

启动和续接表单显示实际 Pi 版本、配置目录、供应商、模型和本机凭证检查结果。配置指引中的登录和模型列表命令使用工作台实际采用的 Pi 可执行文件和配置目录。内置供应商可用 `/login` 登录或配置其 API Key。自定义供应商和模型在显示目录的 `models.json` 中配置。为新运行保存默认模型时，在 Pi 的 `/model` 选择器中按 `Ctrl+S`，或在同一目录的 `settings.json` 中设置 `defaultProvider` 和 `defaultModel`。保存后回到工作台点“重新检测”。修改目录覆盖或凭证环境变量时，需从设置了新值的终端重新启动工作台。

列表反映本机 Pi 的模型和凭证状态。凭证检查通过后，可主动点击“测试模型连接”确认当前账号是否能调用所选模型。测试在独立临时目录发送一条固定的简短消息，可能使用少量模型额度。供应商提示当前 ChatGPT 登录不支持所选模型时，可改选该账号支持的模型。方舟返回 `InvalidSubscription` 时，到供应商控制台核对套餐状态和专属 API Key。

新 Pi 会话在“运行设置”按产品 Home 查看已登记的工程，也可以从已登记工程中手动选入。离线命令就绪时，普通新会话和续接中的参与工程默认选择“编辑并运行离线命令”，可按工程改为“编辑”或“只读”。命令隔离不可用时，默认选择“编辑”，工作台拒绝要求执行命令的任务。核对实际路径、分支和 HEAD 后发送。已有 Git worktree 可单独登记。普通续接沿用工程集合，每轮可重新指定权限。需要增加或替换工程时，选择“扩展工程范围并继续”，带原任务进入默认只读的新会话。

编辑直接写入选定检出，取消或失败后已写入内容会保留。新会话的离线命令可读取已选工程，写入限于该命令指定的工程与临时目录。macOS 使用 Seatbelt 保护 Git 和 YSS 控制文件。构建和测试使用已准备的依赖。Maven 和 pnpm 缓存也可在启动工作台前用 `YSS_PI_MAVEN_REPOSITORY` 和 `YSS_PI_PNPM_STORE` 指定，例如 `~/Library/pnpm/store`。

Windows 的离线命令就绪检查覆盖文件和网络隔离、Node.js 测试及进程树清理。网络检查使用本机可达的 IPv4 或 IPv6 端点。断网且仅剩回环地址时，工作台核对回环访问拒绝和实际 AppContainer 令牌的无网络能力状态。检查通过后，工作台以 AppContainer 运行系统 `cmd.exe` 和已验证的 Node.js，并用 Job Object 管理取消及异常退出。每次执行一行命令，可用 `&&` 组合并传递失败。命令在当前执行工程的私有副本中运行，可通过 `YSS_PROJECTS_JSON` 定位其他已授权的只读副本。授权范围内含符号链接、目录联接或多重硬链接的文件时，该工程的命令会在复制阶段停止，默认布局的 pnpm 依赖目录可能触发此限制。成功退出并确认进程树清理后，工作台核对原工程授权和文件基线，再通过事务写回可验证的改动。系统或工具链无法通过检查时，工作台显示原因并关闭离线命令。

工作台重启会检查 Windows 命令的暂存记录。能确认命令尚未启动，或已确认整棵进程树停止且无需核对写回事务时，工作台清理暂存副本。已有写回预约时，须确认原工程事务已结束且清理完成。缺少进程树停止证据或事务结果仍待核对时，工作台保留暂存并显示待恢复。

当前轮结束后，可在 Pi 会话打开「本机测试与构建」，选择参与工程及工程内的相对子目录。留空时使用该工程的原始检出目录。点击「本机测试」或「本机构建」时，工作台核对所选路径、分支和 HEAD，使用本机 Node 与 `package.json` 锁定的 pnpm 运行对应脚本。脚本以当前用户权限执行，构建产物写入原工程。退出结果、日志和本次成功构建新增或更新的 `dist` 路径关联到发起时的会话，Pi 续接时可使用结果摘要。

本轮可选入已关联 GitLab 流水线的 Job。设置中核对失败提交 SHA 和检出 HEAD，提交一致时可按同提交复现，版本不同时可选当前检出做对照。两种方式都使用当前检出的文件，包含已有的未提交内容。工作台复用本机 `glab` 针对绑定实例的认证，向 Pi 提供有来源的限量日志节选。自动读取不可用时，可在要求中提供相关节选。

已有 Codex 或 Pi 隔离会话继续保留日志、差异、预览及历史成果接收。后续执行从原 Spec 新建 Pi 会话。Windows 分别检查 Pi 基础作业和离线命令，可在本机诊断中查看两项结果。

1. 从主导航“AI Agent”打开 Pi 工作区，或从 Spec 详情打开“运行 Pi Agent”。主导航优先使用当前可用规格，其次是上次打开的可用 Agent 规格，首次进入按规格更新时间选择。左栏可切换规格并查看其会话，“待处理”可定位需要答复、核对执行状态或审阅成果的会话。新会话在“运行设置”核对参与工程和本轮权限。可以直接读取原工程中未提交的主 Spec 和当前原型。需要跨工程时先选入工程，文件工具使用工程 ID 和工程内相对路径。
2. 进入后可先查看登记会话与编辑草稿，来源核验和 Pi 环境准备分别显示。发送后先收到作业回执，准备期间可停止。会话按顺序展示本轮要求、答复和工具活动。点击“上下文”可查看模型窗口及估算用量，轮次详情显示 Pi 返回的本轮用量和会话累计。Pi 返回可展示的推理片段时，推理项随片段展开和更新，结束后默认折叠并显示用时。手动展开或折叠后沿用该选择。每段保留前 6,000 字符，超出部分以省略号提示。计划和上下文压缩也随运行更新。命令可在执行中展开输出。完成后显示退出码或终止信号，已识别的失败附有诊断提示。上翻可加载更早的内容，也可回到最新。业务问题在原轮作答，保存后显示答复 ID。“本轮日志”可查原始事件。
3. Pi 结束后，工作台固化本轮成果。“执行成果”按工程显示文件清单，展开文件查看变化，按需打开全文或选行返工。只读轮次留存主 Spec 和关联材料。编辑轮次按运行前和结束版本展示文件变化，轮前已有的未提交内容纳入起点。原型有可用构建入口时可打开预览，交互结果以实际操作为准。采集失败时查阅本轮日志并核对原工程。
4. 历史隔离成果仍可选中文件后接收。冲突需明确采用隔离结果，文件版本改变后须重新核对。直连编辑后的结果已经写入原工程，可直接从执行成果审阅。
5. 在同一会话输入后续要求，续接沿用原 Spec 和参与工程，每轮按原工程当前内容重新取得起点。切换分支或更换参与工程后，从原 Spec 新建会话。返回原 Spec 核对正文、关联材料和问题回写，内容确认仍由用户操作。

同一浏览器标签刷新后可继续编辑草稿或核对原作业回执。使用“加入下一轮队列”可在同一会话安排任务，派发前可编辑或移除。前轮成功且没有待处理成果时，只读队首可以自动发起。编辑原工程的任务在队首等待逐轮确认。队列轮次默认关闭离线命令。待答复、待审阅、停止、失败、目标换版、回执待核实或工作台重启时，队列保留任务并显示原因，处理后可恢复。
6. 会话条目右侧的删除操作经确认后移除该会话的工作台记录、日志和成果入口，保留工程文件、隔离 worktree、已保存到 Spec 的答复及 Pi 本机会话文件。会话仍在运行、接收或需要核实事务时，须先处理相应操作。

从工作台的“执行与待处理”打开“全部执行记录”。“执行日志”可分页读活动表和原始事件。“工程位置与执行信息”提供本次宿主设置。“停止运行”只停止当前作业。旧 Pi 记录按已留存的事件回放，未保存原始要求的轮次会在会话中提示。

工作台通过 `GET /api/jobs/{jobId}/activities` 读取最近 50 条聚合活动。添加 `view=conversation` 可获取会话条目、本轮要求与上一轮作业编号。用当前页首行的 `id` 作为 `before` 可读取较早一页。`cursor` 是本次快照已处理的原始事件编号，会话与日志共享从该游标接续的事件流。`GET /api/jobs/{jobId}/activities/{id}` 读取这条活动已留存的完整内容和输出。以上查询均使用当前工作台会话。

每个 Git 工作树快照最多 256 MiB、200,000 个文件，符号链接与子模块会提示受保护对象。Git 跟踪文件、未忽略文件和运行主 Spec 引用的本地资源参与比较，静态原型资源按声明采集。

关闭浏览器后可回到执行详情继续观察。CLI 退出或重启后，原活动作业显示为已中断，具备有效 Pi 会话及原工程绑定时可续接。缺少冻结结果的中断轮次显示待核实，已写文件保留在原工程。历史隔离成果接收时，依据返回差异重新核对选定文件。

接收包含主 Spec 的成果时，工作台先解析所选文件，再核对本次新采纳的答复或延期 ID。若同题已保存更新的答复、原延期已到期，或成果中的问题字段无法读取，本次选定文件保留原样。同一 Pi 会话已接收过该主文件时，再次回写核对最近一次接收的同题内容。原件中的题意或待采纳的决定后来变更时，按当前依据修订后再审阅差异。

仅接收附件时，按已登记主文件核对答复归属。只与隔离稿里的新问题或新版本匹配的答复保留在运行记录，可在实际接收对应主文件后纳入个人记录。重新接收同一版本的主文件时会补齐符合来源的旧漏登答复，原文件字节和文件接收记录保持一致。接收期间可继续查看和处理其他问题，工程根及主文件路径待本次接收完成后再改。

续办文本分别显示所读主文件的 `contentStatus` 和工作台综合问题、答复及确认得出的个人状态。Pi 续接时按本轮开始实际读取的主文件报告内容状态和摘要，材料版本单独标注。局部回写沿用整份规格原有的内容状态。

常规答复回写保留题意，更新 `status`、`resolution`、`appliedDecisionId`。延期原因、影响、排除范围、复查日期及时区或复查条件写入原条款或 `resolution`。本次授权修订规则且业务前提确有变化时，沿原 FR、AC 或前置问题找到受影响的原题，在保留 ID 的前提下更新题意或影响。原答复保留供复查，只需核对的独立问题沿用其原状态、答复和条款。

## 草稿、并发修改与版本比较

Spec 个人信息、问题答复和阶段进度表单支持本机草稿。看到“草稿已保存到本机”后，重载页面或重启工作台可从“可恢复草稿”恢复。恢复后核对内容并正常保存，草稿保存错误会保留当前输入并显示原因。

另一页面或 CLI 已更新同一编辑目标时，页面展示开始编辑时、当前输入和最新记录。逐字段选择冲突内容，合并后再次保存。恢复旧草稿时也会核对其原基线，保存成功后移除已采用的草稿。

在内容区选择“与确认版本比较”，默认对照历史确认与本轮实际确认材料。切换到「当前来源」可单独核对实时文件。两种比较都支持显示新增、修改、删除和逐行差异，二进制资源展示大小和摘要。图片可按需加载，历史 HTML 原型可直接预览，确认版本的文件可下载原字节。对比文件变化后需重新比较再查看。旧确认若仅有摘要会显示“历史正文未留存”。当前完整产物摘要与旧确认一致时，可补存快照并保留原确认时间。

## 主 Spec 与内容确认

一个主 Spec 关联业务正文、交互说明与原型，草稿始终可阅读。无项目既有约定时，新需求默认 `docs/spec/<YYYY-MM-DD-topic>/<YYYY-MM-DD-topic>-spec.md`；分文件交互说明使用同目录同前缀 `-interaction.md`，可选独立产品设计说明使用 `-design.md`，新独立原型放 `prototypes/<YYYY-MM-DD-topic>/`。日期固定为首次创建日期，topic 为具体英文 kebab-case；同需求续改复用，独立新范围另建，同名先核对不覆盖。旧 `docs/spec/topic/spec.md`、`interaction.md` 及其他合法 Markdown 路径仍可用，不自动迁移。

`register` 是可重复的登记/刷新入口，保留现有主 Spec 的启用状态。本次源码只将同目录同前缀、无自身元数据且被主文档 `resources` 明确本地引用的交互说明（kind=interaction）或设计说明（kind=supplement/other）归主。旧 `interaction.md → spec.md` 保留无元数据推断；有元数据的旧主文档须明确引用该本地路径，兼容其既有资源 kind。自身有效 `yss-spec` 元数据始终独立，普通参考文档、不同前缀/目录、仅个人资源或正文链接不构成新附件归属。发现扫描只读；主文件 register/refresh 才停用符合条件的旧附件记录，单独刷新附件不合并，个人备注、答复和历史保留。识别失败在发现结果中告警并标记不完整，不作为可登记候选；坏附件不会导致合法主文件刷新时被误停用。

已登记文件需要改名时，先核实原数据目录、Spec ID 及新路径未被任何启用/停用记录占用。安全改名并更新正文链接、来源和个人资源后，通过原 Spec 的“主规格相对路径”编辑保存，再 register 新路径，核对仍为原 ID。编辑指向已归属附件的路径会拒绝；普通标记编辑不受影响。不能先登记新路径再合并，也不能靠停用释放路径。路径参与摘要，纯改名后旧确认只留历史，须重新核对确认；中断时修复原记录，不创建补偿 Spec。本次源码能力不等于已发行或已安装版本能力，须用实际程序验证。

来源元数据管理的资源会随刷新新增、移除或改路径，个人手工资源保留；主文件中的单个 JSON 注释块维护产物和问题。以下旧路径示例仍兼容：

```markdown
<!-- yss-spec {"schemaVersion":1,"scope":"用户新增与编辑","contentStatus":"draft","resources":[{"kind":"interaction","label":"交互说明","targetType":"local","target":"docs/spec/users/interaction.md"},{"kind":"prototype","label":"可操作原型","targetType":"local","target":"prototypes/users/dist/index.html"}],"questions":[{"id":"OQ-01","title":"谁可以停用用户？","kind":"decision","impact":"决定停用入口权限","recommendation":"仅管理员","blocking":true,"affectedScope":"停用用户","status":"open","resolution":"","appliedDecisionId":null}]} -->
```

`contentStatus` 由 Agent 声明 `draft` 或 `ready`（缺省草稿）；个人内容状态派生为未标记、草稿、可确认、已确认，与个人工作 Status 分开。`resources.target` 是项目相对路径；远端资源需本地快照才能锁定确认版本。事实问题由 Agent 查证并写明 resolution，业务问题通过工作台或已获授权的 `respond` 保存真实答复。“待确认事项”按卡片展示，可单项或批量复制已保存的有效答复与延期安排，作为提示词交给 Agent。回复先显示待回写；Agent 落实正文、AC、交互和原型后，在原问题保留 ID，写入 `status:resolved`、`resolution` 和实际采用的 `appliedDecisionId`。问题变更后，历史区显示原文和复查原因，本次答复从空白开始。可重新填写或点击「沿用原答复」再编辑，只有成功保存才产生当前问题的新答复 ID。完整 Agent 续办请求单列历史原文，复制有效答复时只包含仍适用的记录。已回写结果可直接引用，重复续办跳过已落实的改动。

延期须记录原因、影响、排除范围、复查日期或条件，Agent 回写为 `deferred` 并引用实际回复 ID。关键问题只能在完整排除其受影响范围后确认剩余范围；确认文案明确列出排除内容。复查日期按答复保存的时区计算。到期当天即使仍待首次回写，原延期也转入复查。页面保持打开时会更新这项状态。旧记录有复查日期但缺少保存时区时，历史区保留原文和原因，由用户重新登记日期及时区或复查条件。条件延期保留触发条件，接手方据实核对。条件已触发时在原问题记录事实并重新打开，保留此前真实采纳记录。打开/刷新时显示待决定、待回写与到期信息，没有后台推送。

只有 Agent 标记 ready、确认材料可读且相关问题已处理后，用户才能确认当前范围与版本。正文和采用的说明仍按字节检查。原型确认包含实际运行包，同一个构建目录由多份 Spec 关联时，各自采用其已确认的运行包。详情可同时查看已确认快照、最新版预览和变化路径。

确认的共同材料或共用原型有新版时，当前 Spec 可以继续引用自己的已确认版本。声明了消费范围的依赖发生变化且影响未知时，交由 Agent 核实。Agent 可用 `workbench review-materials` 记录参考资料、依赖范围及核实依据。影响已定位且新版就绪时，列表显示一次「新版待确认」；从该筛选可找到已完成的 Spec。旧记录仅存摘要时，精确匹配可沿用。失配时显示历史缺口并核实当前材料。个人状态、内容确认和已验收目标各有独立记录。

## 数据与恢复

个人数据使用 `ProjectDirs::from("com", "ysstech", "yss-workbench").data_local_dir()`；终端启动信息显示实际路径。`workbench.sqlite3` 保存项目、Spec、任务、阶段记录、收藏视图、问题答复、范围确认和 before/after 历史。`state.json` 在迁移后只保存存储标记，用于阻止旧程序继续写 JSON；不要删除该标记。`lock` 仍保护单服务进程，SQLite 编入 CLI，用户无需安装数据库。

每条记录分别保存，变更、历史与 revision 在同一事务提交。两个页面保存同一旧版本时拒绝覆盖；数据库忙且已回滚时可以稍后重试。结果不确定时停止接受写入，须重启核实后再操作，不能反复提交。不要用数据库工具直接编辑运行中的库。

主记录逻辑状态沿用 16 MiB 和最多 100 万节点等结构限制，草稿、作业、事件与确认字节对象另存于 SQLite 扩展表。“设置”展示数据库及分项用量。CLI 查询仍使用完整内存快照，浏览器列表、历史和日志按各入口分批读取。损坏、未知结构、数据库与标记冲突均保留文件并报错，不自动重置或回退旧备份。

### 从设置创建一致备份

1. 在“设置 → 备份与恢复”填写新的备份归档绝对路径，选择“创建备份”。服务运行期间通过 SQLite 在线备份生成一致数据库，归档清单校验完成后发布文件。
2. 从执行记录确认备份完成并保存归档。个人记录、草稿、作业、冻结成果字节对象和已有迁移备份随个人数据备份保存。Pi 会话留在原工作台数据目录的私有会话路径，恢复后的数据目录用于审阅和接收冻结成果。工程源码及运行依赖按各工程的方式管理。
3. 在“恢复到新的数据目录”填写归档和新的或空的个人数据目录，选择“校验并恢复备份”。目标须位于 Git 工作树及登记工程之外，父目录已存在。
4. 恢复完成后按返回命令以 `yss workbench --data-dir <恢复目录>` 打开新工作台，核对工程路径、Spec、答复、确认与执行记录。当前服务继续使用原数据目录。 已冻结的历史运行可在执行详情选择“核对工程绑定”，确认当前登记路径、分支与 HEAD 后重新绑定，再重新审阅差异。仓内工程前缀与分组布局须对应，原隔离工作树的身份记录保留，续接另行校验实际工作区。

### 纯 CLI 或旧版的离线目录备份

已安装版本尚无“创建备份”入口，或采用纯 CLI 维护时，先退出工作台并确认进程已停止，再复制整个个人数据目录，包括数据库、存储标记和尚存日志。恢复时保持服务退出，使用同一份完整目录备份及匹配的程序打开。异常退出留下的 SQLite 日志由新版工作台在启动时恢复，纯查询需要写入恢复时会提示启动新版工作台。

刷新失败时保留上次快照并显示读取时间。源目录丢失、断开或文件删除不会删除个人状态。支持草稿的表单会显示本机保存状态，离开前核对保存结果，重载后可恢复已保存的草稿。

## 构建

源码构建顺序见 [构建说明](build-install.md)。UI 使用 Vue 3、TypeScript、Vite、pnpm；Rust 用 AssetLoader 注入静态资源，只有用户二进制内嵌 `ui/dist`。构建摘要覆盖 UI 源码、配置、锁文件和实际产物。发布包仍只包含 `yss` 与发行清单，没有额外运行时服务。

正式平台沿用 macOS ARM64 与 Windows x64。各次实际构建、原生运行和 CI 结果分别说明，未运行的平台不能视为验证通过。

## JSON 升级与恢复

旧 JSON v1/v2/v3 均可迁入 SQLite。纯查询继续只读旧文件；首次启动新版工作台或执行写入命令时自动迁移，即使该业务操作最后没有产生状态变化。迁移保存全部已有记录，包括隐藏任务；不改变 ID、revision、历史顺序或业务状态。旧工作台运行时须先退出，不会强制停止旧进程。

迁移先按原文件字节 SHA-256 保存 `state.v<原版本>-backup-<sha256>.json`，验证临时数据库后再切换存储标记和正式库。重复备份只接受完全相同的内容，不覆盖冲突文件。切换前失败时原 JSON 不变；切换开始后失败，原内容仍在已验证备份中，下次启动可续接已确认的中间状态。无法证明文件归属时明确报错，不猜测哪份最新。

查询遇到 preparing 标记时提示启动新版工作台继续迁移；库缺失、损坏或标记不一致时不会自动从旧备份重建。`workbench-migrate-*.sqlite3`、`sqlite-marker-*.tmp` 和 `backup-*.tmp` 不能被手工当成最新状态使用。

迁移后旧版 CLI 无法读写同一目录。确需退回旧版时，先退出工作台并完整保留当前目录，再将经过摘要核验的升级前 JSON 备份复制为另一个独立数据目录的 `state.json`，用旧版已有的 `--data-dir` 指向它。该备份不包含升级后的修改；不要覆盖当前 SQLite 数据目录。

## 只读查询

```text
yss workbench query --entity task --project <ProjectID> --status doing --status blocked --json
yss workbench query --entity spec --activity all --include-closed --json
yss workbench query --entity task --q 接口 --stage implementation --stage verification --sort titleAsc --json
yss workbench query --source-problems --json
yss workbench query --entity spec --content-status draft --reminder writeback --json
yss workbench query --entity spec --needs-reconfirmation --json
yss workbench lifecycle --spec <SpecID> --json
```

`--project`、`--spec`、`--stage`、`--status`、`--content-status`、`--reminder` 可重复；未知项目／Spec ID 返回空结果，不扩大范围。`--activity active|inactive|all` 默认 active；任务有效启用同时要求任务、父 Spec、父项目启用。排序支持 `updatedDesc`（默认）和 `titleAsc`，相同键以 ID 稳定排序。内容状态为 `unmarked|draft|ready|confirmed`，提醒为 `decision|research|overdue|writeback|ready`，`--needs-reconfirmation` 筛选确认后产物已变化的 Spec。内容筛选用于 Spec，已有任务的对应内容字段为空。外部链接不计为来源异常。CLI、HTTP 和界面复用相同查询语义；读取不创建数据目录。

JSON 信封 command 分别为 `workbench.snapshot`、`workbench.query`、`workbench.lifecycle`。query 返回 revision、readAt、total、items；lifecycle 返回 Spec、八节点、任务和真实历史。HTTP 的 `/api/query`、`/api/specs/{id}/lifecycle` 使用相同的本机会话保护。没有通过 CLI 自动执行任务、提交 Git 或写回第三方平台的功能。

### 核实已登记的 Spec

在终端运行 `yss workbench spec-status --spec-id <SpecID> --json`，即可只读核对一条已登记的 Spec，包括其来源诊断、内容确认条件、问题状态和有效进度。自定义数据目录沿用启动工作台时的 `yss workbench --data-dir <目录>`。只知道标题或路径时，先用 `query --entity spec --q <关键词> --activity all --include-closed --json` 获取 `result.items[].specId`。

先查 `result.sourceHealth` 和 `result.sourceMessage` 确认来源是否可读，再用 `content.status`、`content.canConfirm` 和 `content.blockers` 核对内容确认条件。已有确认的范围和版本见 `content.confirmedVersion`，可对照 `content.artifactDigest` 和 `content.observedArtifactDigest` 核实当前采用版本及登记工程的材料变化。隔离工作区的实际可读版本应在对应执行记录核对。有效阶段和下一步见 `progress`。需要阶段记录、任务和历史时用 `lifecycle`，需要接续要求和问题答复详情时用 `request`。完整参数及字段见 [命令参考](cli-help.md#核实单个-spec-状态)。
