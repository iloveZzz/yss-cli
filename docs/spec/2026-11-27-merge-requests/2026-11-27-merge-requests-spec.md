## 目标与范围

工程协作者进入 YSS 工作台的「合并请求」，可在同一列表浏览已登记且启用的工程对应的 GitHub Pull Request（PR）和 GitLab Merge Request（MR）。用户可以找出待处理请求，回查已合并或已关闭的请求，先在工作台了解摘要，再前往对应平台处理。

当前工作台分别登记本地工作树，支持核对产品 Home 的仓库地图，也能用本机已认证的 `gh` 和 `glab` 读取用户已关联的单项远端记录。新增入口按合格仓库聚合浏览。已有「研发关联」及 Spec 阶段证据继续由各自入口管理。此前 Pi Agent 规格将 PR/MR 列为独立范围，本规格覆盖其中的只读浏览。 [工作台项目与研发关联](../../workbench.md#工程维护与产品-home) · [Pi Agent 对话与执行工作台](../2026-11-25-pi-agent-workspace/2026-11-25-pi-agent-workspace-spec.md#目标与范围)

本次提供来源范围管理、列表筛选与分页、请求摘要及原站入口。用户在原站阅读完整讨论、提交与文件差异，执行评论、审批、关闭、重开和合并等操作。登录授权、登记工程和维护 Git 远端继续使用已有入口。后台订阅、通知和离线浏览属于范围外。

本次增补解决两个等待场景。用户进入「开放中」或查找已知编号时，尽快看到当前条件下可排序、可打开的结果。用户打开请求后，可以先阅读 Markdown 描述和基础信息，评审与 CI 随各自的读取结果逐项呈现。

## 使用者与任务

| 任务 | 用户条件与动作 | 可观察结果 |
| --- | --- | --- |
| 查看当前待处理请求 | 已登记工程的协作者进入一级菜单 | 可在默认「开放中」列表同时查看 GitHub 与 GitLab 请求，知道哪些来源读取成功、哪些需要处理。 |
| 查找历史请求 | 选择状态、平台和仓库，输入标题或编号并翻页 | 在选定范围内找到目标，查看详情后可继续原列表位置。 |
| 核对或调整来源 | 遇到多个远端、产品 Home 绑定变更或管理员镜像时查看来源 | 可确认已有工程的候选远端是否纳入，知道它对应哪个平台实例和仓库。 |
| 核对摘要或前往原站 | 有当前远端读取权限的协作者打开请求 | 可定位请求的分支、作者、状态与关键时间。原站保留对应账号的读取和操作权限。 |

## 功能规则

### FR-01 进入合并请求列表

「合并请求」作为 YSS 工作台一级菜单，与 Spec、工程等入口并列。打开页面时直接查看所有合格来源，默认选中「开放中」。用户无需先选择 Spec、产品 Home 或单一仓库。平台筛选提供 GitHub 和 GitLab，仓库筛选按实际纳入的远端仓库显示命名空间和仓库名。同名来源用平台和实例区分。

合格来源须关联至少一项已登记、启用的 Git 工程，且可核对平台、实例和远端仓库身份。仓库列表按远端身份归并，候选来源的本机工程归属可在「仓库来源」查看。远端读取使用工作台对该平台实例已配置的本机连接及其现行权限。工程停用、移除或已无法核对身份时，移出其失效的来源关联。拥有其他合格工程关联的同一远端仍可读取。

GitHub.com、GitLab.com 和可识别的自建 GitLab 实例均在浏览范围内。GitHub Enterprise 实例仅在能明确核对平台、实例、仓库及对应现有连接时可纳入。自建实例的实际版本、字段可用性与权限需按真实环境验证。

### FR-02 从登记工程确定远端来源

按工程核对候选来源，可用的默认来源与用户显式选择的额外来源共同构成浏览范围。默认采用以下顺序。

| 工程所处情形 | 采用结果 |
| --- | --- |
| 当前有效且已核对的产品 Home 绑定指向唯一远端 | 默认采用该绑定的远端。 |
| 工程没有有效的产品 Home 绑定，且 `origin` 可独立且唯一识别，仓库身份没有冲突 | 默认采用该 `origin`。已有 Home 绑定失效时，在「仓库来源」标明改按 `origin` 读取的原因。 |
| Home 与当前 `origin` 的仓库身份有冲突，或 `origin` 无法唯一识别 | 在「仓库来源」显示需核对及原因。待核对项暂停自动纳入，用户可核对 Home 绑定，或确认采用该工程中可识别的候选远端。 |
| 工程没有 `origin`，或用户需要查看 `upstream`、镜像等额外远端 | 用户从已登记工程的可核对候选中明确选入。即使此时只有一个非 `origin` 远端，也由用户选择。 |

「仓库来源」显示参与工程、来源依据与平台实例下的完整仓库路径。用户可加入候选远端或撤回自己加入的来源。身份变化后，旧选择只对应原远端，新身份需重新核对。撤回操作仅移除所选的额外来源关系，同一远端可能仍因默认来源或其他工程保留。

同一平台实例中的同一远端仓库，即使通过多个 worktree、访问协议或远端别名出现，也只查询和展示为一个仓库。仓库的短名称、Git 远端别名和请求编号都可能重复。同一仓库内请求以该平台的仓库内编号区分，所以跨仓库、跨实例的同编号请求保留各自条目。不同 fork 或镜像可各自拥有独立的合并请求。

### FR-03 统一状态和列表信息

列表包含标题、平台、仓库、仓库内编号、作者、创建时间、更新时间、状态及草稿标记。GitHub 展示 `#编号`，GitLab 展示 `!编号`。草稿是请求的独立属性，仍打开的草稿归入「开放中」。平台未提供可用值的字段标为「不可用」，特别是草稿字段缺失时避免默认显示为普通请求。

| 状态视图 | 包含的请求 |
| --- | --- |
| 开放中 | 平台确认仍处于打开状态的请求，含打开的草稿。 |
| 已合并 | 平台确认已合并的请求。 |
| 已关闭 | 平台确认已关闭且未合并的请求。 |
| 全部 | 当前权限和过滤条件下可取得的请求，以上各组去重合并。平台返回请求但其状态无法核实的，在「全部」显示「状态不可用」。 |

GitHub 的 `closed` 值同时可能对应已合并和未合并关闭。工作台使用平台能确认的合并事实完成区分。如果只取得 `closed` 且无法确认是否合并，该请求仍可在「全部」查看，状态标为不可用。

标签数量以当前平台、仓库和搜索条件下该标签的完整结果为口径，包括尚未浏览的分页。只有能核实整个范围的准确数量时才显示数字。状态无法核实且可能改变标签总数时，受影响的标签省略数字并提示原因。部分读取、权限异常和平台上限也按其影响范围处理，单页数量及已读部分都不充当总数。

### FR-04 组合筛选、搜索与历史浏览

状态、平台、仓库及搜索条件共同生效。文字搜索匹配标题片段，搜索范围跨当前条件下可读取的全部历史分页。纯数字按完整编号匹配，也可输入 GitHub 的 `#编号` 或 GitLab 的 `!编号` 限定编号标记。相同编号在多个选中仓库命中时可同时返回，用户根据平台与仓库区分。

默认按「更新时间」从新到旧，可切换为「创建时间」从新到旧。排序对跨仓库的结果整体生效，时间相同的条目保持稳定顺序。相同条件下对同一组结果翻页，每条匹配请求只出现一次且均可到达。筛选、搜索或排序变更后从第一页读取。关闭详情恢复原查询、排序及页码，页面仍有该请求时可回到原行。

「已合并」「已关闭」和「全部」可继续查找远端仍能提供的历史。工作台不设固定历史日期截断。分页、搜索或远端限制导致结果不完整时，按来源显示范围受限和已取得结果，并提供去原站继续查找的入口。列表分页与搜索都不能把已读取的首批数据当作全历史结果。

首批结果可用后即可浏览。仍在核对其他来源时，提示覆盖尚未完整，只有位置已能确定的记录进入当前分页。未取得足够依据的时间并列记录继续等待。当前页已有足够结果且顺序可确认时，历史读取不阻塞该页面。某来源失败后，成功来源可按已取得范围继续浏览，并明确标记缺失范围。重试恢复后，按当前条件及实际数据重新汇总，同时保留过滤、排序和能继续定位的条目。相同查询刷新或继续读取时保留仍适用的结果；切换条件从第一页显示新查询，并忽略旧条件随后返回的响应。

打开「开放中」时，首屏读取仅为开放请求所需的范围。其他状态的总数可稍后补齐，无法核实时暂不显示。精确编号按所选仓库和平台核对对应编号，其他状态、仓库和编号的结果不混入。无法区分编号不存在与仓库不可访问时，呈现当前来源的核对结果及原因。

### FR-05 查看只读详情并打开原站

点击请求在工作台打开只读详情抽屉，桌面和窄屏均能阅读并关闭。详情显示请求标识、标题、所属仓库、状态、草稿、作者、描述、来源分支和目标分支，以及已核实的创建、更新、合并或关闭时间。描述为空时显示「无描述」，描述读取失败时提示对应原因。实际分支所属仓库可取得且有助于区分 fork 时一并展示。

详情设「评审与审批」及「CI」两个独立区域，仅展示来源平台能够确认且当前账号可读的适用状态，例如「已批准」「有变更请求」或「CI 失败」。时间和适用的提交或分支可核实时一并显示。只有旧提交的 CI 可读时，在用户展开历史记录后标明对应提交及其历史状态。如平台确认没有相关记录，可显示「暂无记录」。字段或权限缺失时显示「不可用」，保留可读的基本详情，并引导用户在原站核对。评审、CI 和请求状态分别呈现，可合并性由原站判定。

点击列表行时，抽屉立即用该行已核验的标题、编号和仓库标识定位请求。基础详情核验后先显示描述、分支、作者与时间。「评审与审批」和「当前 CI」各自显示加载及读取结果。平台和当前请求类型支持查询历史 CI 时显示展开入口，用户展开后才读取，并以提交或流水线标识区分历史记录。无记录、读取中、不可用及部分结果使用各自的反馈。摘要遇到临时读取错误时可独立重试，其他已核验内容保持可读。平台确认的流水线执行失败是状态信息，用户可到原站查看。摘要返回时须对应当前请求和适用版本，关闭详情、切换请求、账户变化或撤权后忽略旧响应。若头提交已经变化，旧 CI 可按其真实归属展示为历史，不能充当当前 CI。

GitHub PR 的 `body` 和 GitLab MR 的 `description` 在抽屉内以静态 Markdown 排版显示。支持标题、段落、列表、引用、表格、行内代码、代码块和可安全打开的网页链接。长表格和代码在各自区域横向滚动，窄屏正文正常换行。外部图片用带说明的占位呈现，内嵌 HTML 作为文字显示，仓库相对地址及本机、工作台页面或控制入口不从描述中打开。平台专有语法在工作台不能还原时保留可读文字或代码，用户可通过原站入口查阅。保留「无描述」和「描述不可用」两种状态。

「在原站打开」指向该请求的真实平台、实例、仓库及编号，继续使用原站会话和权限。工作台按只读内容呈现外部文本，描述中的内嵌内容不得触发脚本、自动下载或工作台操作。

### FR-06 刷新、部分结果与恢复

进入页面时发起读取，也可主动刷新。按来源反馈读取结果，诊断可指出需核对的仓库、连接或权限，并支持在处理后重新读取受影响来源。部分来源失败时，仍可搜索、翻页和查看当前查询中已取得且有权限的内容，页面提示覆盖不完整。刷新和重试保留当前条件。列表和详情只接纳仍适用于当前查询、仓库身份和读取权限的响应。切换查询条件后忽略前一查询尚未完成的响应。关闭详情后忽略该次详情的延迟响应。发现权限撤销后，忽略该来源尚未完成的旧响应。

| 条件 | 页面可见结果与恢复 |
| --- | --- |
| 没有合格来源 | 显示「暂无可浏览仓库」，可查看来源及已有的工程登记入口。 |
| 合格来源全部读完，当前条件匹配零条 | 显示「没有匹配的请求」，可调整或清除过滤条件。 |
| 部分来源发生网络错误、限流或远端范围上限 | 保留成功来源的结果并提示覆盖不完整。列明受影响来源和原因，可重试受影响来源，遇到平台限制时可到原站继续。成功来源匹配零条且没有可展示的旧结果时，仍显示覆盖不完整及来源原因，受影响的标签总数保留未知。 |
| 网络或限流造成暂时失败，已有同账号同来源、适用于当前查询的可用结果 | 可继续显示该结果，同时标明「上次成功」时间和数据未更新。恢复后用本次结果替换。 |
| 缺少本机工具、尚未认证或当前身份没有权限 | 提示检查现有连接或权限，详情和列表隐藏该来源的受限数据。更换连接身份、仓库身份变化或权限明确撤销时，已有结果不得继续展示。 |
| 有合格来源，本次无法得到任何可展示结果 | 显示读取问题及对应恢复动作。标签数量保留未知，避免以零表示读取失败。 |

用户在列表和详情中仅执行读取。加入或撤回额外来源的作用范围是工作台个人浏览偏好。工程登记、Git 文件与远端平台状态由其原有操作入口管理。工作台保持现有会话保护，页面和错误反馈不暴露凭证或登录信息。

## 验收

| 编号 | 关联 | 前提与操作 | 可观察结果 |
| --- | --- | --- | --- |
| AC-01 | FR-01 | 工作台登记并启用了一个 GitHub 工程及一个自建 GitLab 工程，各有一条打开的可读请求。另有已停用工程、未登记目录及未知远端的本地工程。没有打开任何 Spec 时，进入一级「合并请求」，依次选择平台和仓库。 | 默认「开放中」汇总两家平台的请求。停用、未登记与无法确认身份的仓库均不进入查询。平台和仓库筛选准确缩小范围。停用一个只由该工程关联的仓库后，刷新移除其结果。 |
| AC-02 | FR-02 | 工程 A 的有效 Home 绑定与 `origin` 同指主库，另有 fork 远端。工程 B 是同一主库的另一工作树，其 `origin` 用不同协议访问。工程 C 只有 `upstream`。工程 D 的 Home 地图已过期，但 `origin` 可独立确认且仍是原仓库。工程 E 的旧绑定与当前 `origin` 身份冲突。进入列表，在「仓库来源」加入 A 的 fork 和 C 的 `upstream`，再撤回 fork。 | 主库默认只出现一次，A 的 fork 与 C 的 `upstream` 须在明确选入后出现。撤回 fork 保留主库和已选的 `upstream`。D 从 `origin` 读取并说明原因。E 显示需核对，暂停自动纳入。两个仓库各有同编号请求时，两条均保留。 |
| AC-03 | FR-03 | 来源含一条打开草稿、一条平台确认已合并的 GitHub PR、一条关闭未合并的 GitHub PR 和一条 GitLab MR。切换四个状态标签。再模拟一条 GitHub `closed` 缺少合并事实，或仅某个来源的历史读取受限。 | 列表字段齐备，打开草稿仍归入「开放中」。已合并与已关闭互不重复。「全部」可显示无法核实状态的条目并明确标记。完全读取时数量覆盖全部分页，受未知状态或读取限制影响的总数省略。 |
| AC-04 | FR-04 | 两家平台有同编号请求。多个仓库的请求按时间交错，一组同时间条目分布在分页边界。不加搜索时，目标标题排在首批已加载记录之后，另一条仅描述包含该词。按平台、仓库和状态组合筛选，分别检索标题词、纯数字和带标记编号，切换排序并翻页，再打开和关闭详情。 | 标题搜索可找到较早的目标，搜索结果排除仅描述命中的条目。编号相同的合格条目按所属仓库区分。默认和切换后的排序均横跨来源。同一结果集翻页时，同时间顺序稳定，条目无重复或遗漏。关闭详情保留条件、排序及页码，改变条件回到第一页。 |

## 查询优化与验证方法

11 月 28 日以当前工作台和 yss-cli 源码 `b879e5e` 调查。真实样本观察实际连接；该提交的本地调试构建用于隔离实验，定位与远端网络无关的重复工作。统计中的单页指单个仓库的读取请求。样本数量不足以制定线上时延上限。

| 样本 | 观察结果 |
| --- | --- |
| 当时运行的本机桌面工作台，一个纳入的 GitLab 来源 | 来源核对约 0.70 秒，首个列表页约 5.87 秒后返回网络错误。 |
| 隔离工作台，登记一个可读的真实 GitHub 仓库 | 首个列表页两次为 5.82 秒和 3.03 秒；一次详情约 10.42 秒后返回网络错误。 |
| 隔离工作台，6 个 Git 工程，各配置两个远端，模拟平台每次等待 100 毫秒 | 来源核对 3.45 秒。连续两页耗时 7.22 秒和 6.84 秒，每页各记录 120 次本地 Git 调用和 3 次平台调用。常规详情 7.63 秒、7 次平台调用；带历史 CI 的样本 10.70 秒、24 次平台调用。 |

方案先减少同一查询反复核验全部工程的成本，再按当前状态或编号缩小平台读取范围，同时把基础详情从评审与 CI 的等待中移开。来源核验可在同一查询内复用，变更的本地仓库配置、Home、纳入选择、账号和权限必须重新核对。适用实例可用平台筛选缩小范围。GitHub 已关闭记录仍要按平台确认的合并事实分类，平台标题搜索只有在能确认覆盖时才可用于声明完整结果。实现可结合排序边界调度待查仓库，避免少数慢响应占住其他可开始的读取。并发、缓存寿命、接口和存储结构由研发按实测决定。[本地核验链路](../../../src/workbench/merge_requests.rs) · [分页和详情读取](../../../src/workbench/merge_requests/providers.rs) · [GitHub 搜索限制](https://docs.github.com/en/rest/search/search#about-search)

使用同一版本的样例仓库、相同查询、相同模拟延迟重复对照，记录提交查询到首条可操作结果和首屏排序确认的时间，以及点击请求到正文可读的时间。同步记录本地 Git 检查与各类平台调用次数。通过对照确认，在来源和账号未变的一次查询中，连续翻页不再逐页扫描全部登记工程。中途更换账号、撤销权限或修改 Home、`origin` 后，旧结果应按实际核验失效。原型验收可见顺序和恢复行为；正式候选另对照优化前后请求量，并复验真实 GitHub 与一个实际使用的 GitLab 实例。分别记录成功、部分失败和网络错误，回归原 AC-01 至 AC-07。
