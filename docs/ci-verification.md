# CI 验证与耗时排查

目标是缩短真实验证的等待时间，同时保留完整的选择范围、失败退出码和发行门禁。

## 已确认的问题与改动

Run `38107712055` 的验证步骤实际运行 51 分 39 秒后失败：显式 full 选择了全部包，`-p 1` 顺序执行，governance 累计耗尽 30 分钟包超时；不是最后一个测试独自运行了 30 分钟。项目升级测试使用已退出当前快照的 `.codex/config.toml`；事务测试在任意写入时刻杀进程，偶发命中应被安全拒绝的半成品；两项原生治理 fixture 的指纹绑定了模板源，而消费者读取的是原生 seed 中的来源。

- Bundle 仅对当前可执行程序的不可变嵌入归档缓存已解析、已验证的 Profile；每个调用方获得独立的可变容器。外部归档仍每次完整校验。局部 Linux 热加载基准中，Spec 从约 185–231 ms / 175,308 次分配下降到 0.11–0.18 ms / 303 次分配；这不等于 macOS CI 总耗时。
- 升级测试改用当前受管 `.nvmrc` 验证删除、改名和 missing-base。中断测试观察实际临时文件写完后杀进程，并另外保留部分写入必须拒绝的真实进程用例。
- 升级器的准备目录测试在真实持久化 checkpoint 通知父进程，避免靠大文件和毫秒轮询制造观察窗口。原生恢复验收的强杀用例先暂停实际候选进程，确认目标临时文件已发布，再杀进程；不编辑目标或 journal，不放宽恢复校验。Unix 使用 SIGSTOP/继续信号，Windows 使用进程暂停/恢复接口；各平台仍须实际运行验收，交叉编译不代表通过。
- `native-fixture-register.mjs` 只适配固定模板的 synthetic fixture producer，将平台指纹绑定到它接收的 `nativeSeed`。磁盘模板、来源锁、安装资产与生产校验器均保持原样；fixture 代码形状变化会报错，后续上游修正应移除该适配。
- 少量白名单治理测试复用不可变 seed 资产；键包含二进制摘要、非 root 参数和环境。每个调用方得到独立文件副本，事务目录不移植，未知运行状态、软链接、绝对旧 root 与资产漂移均拒绝。初始化边界和恢复测试仍真实执行初始化。

## 同一份选择与执行清单

`verification-plan.mjs` 先按差异及依赖选择包，再通过 `go list` / `go test -list` 发现顶层测试。重叠选择合并，`verification-tasks.json` 保存测试全集、唯一分配、来源与二进制摘要；定向表达式空匹配直接失败。任务包含轻量检查、CLI、project、四组 governance 及单独的 lifecycle，只有被选中的测试进入任务。governance 默认按名称类别估重均衡；本地可用 `--timings <旧 test-timings.json>` 提供真实耗时权重，旧结果不能代替本次执行证据。

本地示例（准备固定模板及其依赖，设置与 native workflow 一致的 `YSS_*` 环境后执行）：

```bash
node tools/verification-plan.mjs --base <完整基线SHA> \
  --template-root <固定模板源> --out <仓库外目录>/plan.json \
  --report-dir <仓库外目录>/reports --full --execute --jobs 3
```

`--tasks-out <文件>` 只生成可审查清单；随后可用 `node tools/verification-tasks.mjs --manifest <文件> --task <任务ID> --report-dir <目录>` 独立执行。`--fail-fast` 供定位首错，后续未运行项目仍记为未执行，不能汇总为通过。`--slow` 单跑生命周期，不代表全量验收。源码、候选、工具版本、平台或固定模板输入发生变化后必须重新生成清单。

每个任务保留 `test-events.jsonl`、`test-timings.json`、`commands.log`。30 秒心跳列出活动测试，报告按耗时排序；真实非零退出、超时、中断、没有收到预期测试终态都失败。显式 skip 会出现在汇总中，不能称为零跳过全量验收。包级 30 分钟超时是累计时间；普通治理 fixture 子进程最多 10 分钟。完整 Spec/Design/业务生命周期的 Node 生成步骤在首次完整测量中超过 10 分钟，因此单独给出 20 分钟预算；所有子进程仍在包级期限前 5 秒清理。这是防止预算误杀，不是通过延长超时声称性能改善。

## GitHub Actions

`prepare` 构建一次候选、发现测试、上传清单和二进制；`verify` 使用相同的 macOS runner 和固定依赖，最多同时运行 3 个分片，每片内 `-p 1`。任务运行前后检查源码、模板和二进制摘要。`native` 在所有分片完成后核对报告，缺失、失败、重复、未执行或输入漂移都阻止通过，之后才运行既有原生验收与性能检查。慢生命周期是阻断分片，已移除 `continue-on-error`。相同分支的新运行取消过期运行。

Go/依赖下载缓存仅用于准备环境；测试仍 `-count=1`。四组治理估重不保证实际均衡，需要根据首轮 artifact 耗时继续调整；分片也增加准备和 runner 总用量。25 分钟是 macOS 全量验证的优化目标，须由同一提交连续两次真实 Actions 运行确认，不能用本地 Linux 或交叉编译代替。合并后应核对分支保护的 required check 指向最终 `native` 汇总 job。

发行所需原生 82、恢复 12、插件 44、安装 5、历史迁移 48、来源消费者 9 门禁保持原有入口与计数，不以分片通过代替正式发行验收。
