# 工作台 Spec 确认与进度的变更范围

2026-11-23 · 用户采纳本方案及第 5 节的两项行为决定，并授权实施。

工作台应保留每份 Spec 已经确认的内容版本和已经验收的目标。更新其他 Spec、重建共用原型或产生无关 Git 提交时，只在有证据的影响范围内提示下一步。用户打开提醒后，应能看到哪个材料变了、影响哪份 Spec 和哪项验收、由谁处理。

## 1. 本机事实与复现

本机工作台运行 YSS CLI 3.15.0，构建提交 `6ea458f`。用 `query`、`lifecycle` 和确认快照只读核对了截图中的四份 Spec。四份均显示「可确认」「需要重新确认」「进行中」，但问题待决定、待回写和到期数均为 0。该提示来自整份内容版本失配。三份专项有交付确认历史，一期主规格有内容确认历史，交付仍有实际缺口。

| Spec | 最后一份内容确认快照与现状的差异 | 交付事实 |
| --- | --- | --- |
| 新增联系人 | 正文及交互说明字节一致。共用原型的 `index.html` 有改动，原快照中三项构建资源在当前目录已找不到。 | 当前目标有交付确认记录。 |
| 前端加载与过渡体验 | 正文、交互说明和 `loading.html` 字节一致。快照也收录了共用目录中变化的 `index.html` 和同一批构建资源。 | 当前目标有交付确认记录。 |
| 新增患者 | 本专项正文和交互说明有差异。共用原型也有变化。 | 当前目标有交付确认记录。 |
| 一期主规格 | 主文件与最后确认字节一致。患者业务说明 `wiki/patient-care.md` 和共用原型有差异。 | 尚无交付确认记录，生命周期中有验证和交付未完成项。 |

代码有两条独立的触发路径。

1. **内容确认覆盖所有关联文件和原型入口所在目录。** 确认比较 Spec ID、范围与产物摘要。摘要纳入整个主文件、关联资料和原型目录下所有可服务资产。不同入口位于同一个目录，也会收录同一组构建文件。共用主规格等补充资料同样整文件参与摘要。新版摘要无法匹配旧确认时，工作台重新派生内容状态及提醒。[摘要生成](../../src/workbench/content.rs#L428) · [原型资源范围](../../src/workbench/preview.rs#L133)
2. **有效进度按当前产物和整仓版本重算。** 阶段证据受当前 Spec 摘要和目标版本约束。实施、验证及交付还检查工程 HEAD 与整个工作树的摘要。阶段确认摘要也会包含当前工程版本。证据适用性下降后，汇总要求所有适用阶段和交付确认仍有效才能显示「已完成」，于是已有交付记录的 Spec 也可以显示成「进行中」。[工程版本读取](../../src/workbench/progress.rs#L393) · [阶段证据适用性](../../src/workbench/progress.rs#L1174) · [汇总状态](../../src/workbench/progress.rs#L1924)

用 3.15.0 在临时 Git 仓和独立数据目录建立 A、B，两份 Spec 各确认内容，B 另有已确认的本地交付目标。每个场景从同一基线开始。

| 单独执行的变化 | B 的内容 | B 的有效进度 |
| --- | --- | --- |
| 仅改 A 的正文，原型不动 | 已确认，摘要一致 | 已完成 → 进行中，实施证据待同步 |
| 仅改同一构建目录的 `a.html`，Git 仍干净 | 可确认，摘要变化，出现重新确认提醒 | 已完成 → 进行中 |
| 仅新增并提交无关 README，Git 仍干净 | 已确认，摘要一致 | 已完成 → 进行中，实施证据待同步 |

B 在三个场景中的内容确认和交付确认各保有一条历史记录。还原前两个场景的改动后，B 恢复原先的展示。该复现检验了已有行为。SCRM 共用资源变化是否实际影响联系人或加载体验的特定条款，单凭快照字节差异仍待核实。

## 2. 内容版本与资料归属

每个内容确认沿用同一 Spec ID、确认范围和真实产物快照。工作台按这份 Spec 实际采用的材料计算当前候选版本。材料可采用以下方式绑定。

| 材料 | 比较依据 | 用户看到的结果 |
| --- | --- | --- |
| 本 Spec 正文、确认所用交互说明和专属原型 | 读取登记的材料与本 Spec 对应的原型运行包。范围、文件集合或字节变化纳入候选版本。 | 候选就绪时显示「新版待确认」，草稿或阻塞事项显示实际状态及原因。 |
| 确认时采用的共用原型或文档 | 绑定确认快照中的实际版本，继续提供历史预览。有可验证的独立运行包时，可以按本 Spec 的运行包跟踪新版本。 | 共用预览可打开最新版，详情明确标出已确认版本和当前预览各自的版本。选用新的确认材料后才生成相应候选版本。 |
| 实际消费的共用规则或契约 | 声明消费的路径及可定位规则、接口或验收项。按可证实的消费范围判断变更，同一文件中的其他范围可以独立更新。 | 已确定影响时定位到本 Spec 的条款、交互或验收。影响未知的处理见 Q2。 |
| 普通参考资料 | 仍可导航和预览，资料内容进入来源健康检查。 | 更新自身内容时，本 Spec 的既有确认继续有效，新增人工确认数为 0。 |

原型确认应绑定可运行的静态包，包含运行所需的脚本、样式、图片和动态分包。独立构建目录可沿用现有包校验，共用构建优先沿用完整确认快照。若支持按入口跟踪，先有构建产物提供可验证的完整资源清单，再按该清单比较。完整性未知时，最新预览可查，已确认版本仍可重放。

内容确认、差异查看和历史重放使用同一份材料清单。每项记录实际路径、采用方式、材料版本与内容摘要。规格作者或 Agent 在登记本次范围时优先复用已有绑定，新增真实依赖时记录消费依据。有范围变更的共用材料按受影响的原 FR、AC 或接口处理。对照结果关联原确认、新材料版本和影响范围，同一个版本事实在相同 Spec 中只生成一条对应提示。

保留确认材料的字节完整性检查。纯排版变化仍按这份 Spec 自身材料的版本变化处理。材料关联的用途和采用版本变化进入候选比较，保留确认快照中的原材料与原范围。单题答复继续按题 ID、摘要、采纳记录和延期条件判断，涉及旧决定时沿用已确认的复查规则。[主 Spec 内容确认](../workbench.md#主-spec-与内容确认) · [既有答复复查决定](../../../yss-spec-project-template/.template-source/design/2026-11-21-decision-review-handoff-spec.md#1-澄清结论)

## 3. 工程证据和目标完成

### 以验收所用范围判断证据

阶段报告保留实际工程、提交、工作树、目标版本和检查凭证。将参与工程和有依据的输入范围用于适用性判断，例如联系人验收所用表单生成器、联系人接口操作与实际检查配置。工程版本负责定位事实，工作台按报告真正验证的输入决定当前是否需要复核。

目标绑定启动时采用的 Spec 版本，当前候选另行比较。阶段和人工决定基于其实际覆盖的条款、材料、参与工程和证据核实。当前候选版本号变化后，同一目标中的证据可以凭适用范围继续使用。换目标时复用证据须引用来源报告并说明一致依据。只有已展示的确认范围及其依据均一致时，原人工决定才能继续适用。

- **相关输入一致。** 对照原基线与现状的实际输入集合及其摘要，含共享代码、检查配置和生成输入。覆盖完整且相关输入一致时，复用原证据和确认。后续提交继续显示真实提交号。
- **相关输入变化。** 仅受影响的阶段或参与工程出现「待同步」或「需复核」，详情给出对照依据和负责处理的 Agent。联调、合并和环境验证继续绑定实际验证的候选、提交组合与环境。后续提交的验证结果由新证据描述。
- **范围或来源未知。** 路径覆盖不完整、基线不可得或来源暂不可读时，说明缺少哪项证据。活跃目标的对应证据显示「待核实」。旧验证、确认和交付时间继续关联其原版本。

工程证据更新和 Spec 内容确认各自独立。例如只修改当前部署候选的校验代码时，工作台要求核实受影响的验收，内容列仍显示原 Spec 已确认。若工程事实证明应改业务规则，将影响交回对应 Spec 和条款。[现有阶段与证据规则](../workbench.md#自动生命周期跟进) · [上报与版本变化约定](../../../yss-spec-project-template/.template-spec/agents/workbench-progress.md#用户确认与版本变化)

### 显示已交付目标与新的工作

工作台读取对应目标版本的真实交付确认，展示当时的范围、时间、证据和原确认出处。一次刷新、检测到新文件或发现版本漂移只更新适用性和提醒。后续目标沿现有登记入口显式启动，沿用原 Spec ID 并记录新目标版本。已有交付仍可按版本查看。显式退回或更正由原有授权操作记录。

上一轮有真实交付确认、下一轮尚未启动时，进度列显示「已完成」，内容或提醒列显示「新版待确认」「依赖待核实」等当前事实。启动新目标后，进度列展示新目标，详情仍能访问上一轮。当前实际未完成的目标展示其未完成阶段、阻塞和下一步。

### 在列表中找到要处理的事项

- 内容列将同一次「可确认」与「需要重新确认」合成一个入口。打开后显示基线、候选版本、变化路径和影响范围，并复用「与确认版本比较」。
- 清楚标明动作归属。业务确认入口只统计当前范围就绪且确需用户决定的事项，工程待同步和依赖待核实沿进展提醒进入相应详情。资源不可读时以路径和错误提示，当前确认证据需恢复可读后再校验。
- 保留按个人标记或自动进度查看的现有入口。明确按新版待确认筛选时可找到有待办的已完成记录，同时保留「已完成」状态。列表、看板和详情使用同一套判断。已关闭筛选与旧保存视图继续按原条件解释。

## 4. 旧记录接续与实施

升级按原 Spec ID、确认 ID、目标版本和原始摘要读取数据。使用当前可读的旧记录逐项处理。

1. 当前材料、原确认范围和旧算法摘要精确匹配时，直接沿用原确认。采用新清单后若可经快照证明相同范围与材料，记录对应关系，继续引用原确认 ID。
2. 有旧快照且当前只观察到共用目录或参考资料变化时，展示原已确认快照和具体差异。能证明所采用的材料一致则沿用原确认。覆盖范围未知的明确依赖按 Q2 处理。
3. 缺历史文件且旧摘要失配时，显示「历史正文未留存」或「当前适用性待核实」，保留已知的确认与交付事实。取到足够的历史材料后重新核对。单靠旧报告的 `done` 或个人标记只展示其原有含义。
4. 保留来源元数据 v1 的读取路径。`ResourceRef` 与 `SpecMetadata` 在 3.15.0 拒绝未知字段。首轮将明确的材料绑定与适用性记录存在工作台，复用现有确认快照和内容存储。若后续要将依赖范围随 Spec 文件分发，另行设计带版本的输入合同和旧版提示。当前登记及读取可继续使用原 Spec 文件。
5. 在 Rust 后端复用内容与进度投影，向列表、看板、详情、CLI 和 Agent 续办提供相同事实。保留原快照、版本和历史字段，新增可选的已确认版本、已交付目标及差异原因字段。确认提交对当前 Spec 或目标校验实际展示的候选范围、摘要和适用证据。复用现有按编辑目标校验、事务和请求回执机制。其他 Spec 的写操作更新全局 revision 时，可在目标校验通过后继续提交。相关材料变化时，保留输入并提示再次比较。[确认校验及快照](../../src/workbench/content.rs#L554) · [确认快照与差异](../../src/workbench/artifacts.rs#L135) · [按目标校验](../../src/workbench/service.rs#L275) · [查询投影](../../src/workbench/query.rs#L95)

实施可先恢复历史完成和解释提醒，再接入材料绑定与按证据范围核实。工程范围暂不可证实时先显示真实的待核实原因。CLI 入口与模板的上报说明随实际支持的能力更新。

## 5. 已确认的行为

| 决定 | 采用的行为 |
| --- | --- |
| Q1 · 已完成的 Spec 自身改变确认范围内的规则 | 继续显示上一目标「已完成」，标记候选「新版待确认」。显式启动本轮目标后显示该轮实际进度。 |
| Q2 · 明确依赖的共用资料变了，尚无法判断是否影响该 Spec | 进入「依赖待核实」，由 Agent 核对，有证据表明确认范围实质改变且候选就绪后才请用户确认。 |

## 6. 实现后验收

| 场景 | 应观察到的结果 |
| --- | --- |
| 独立 A、B 均已有确认和交付。修改 A 正文，分别测试未提交变化与同仓提交。 | A 按自身材料状态显示。B 继续显示已确认和已完成，人工确认数为 0，原确认与交付 ID 一致。 |
| A、B 使用同一原型项目，不同入口。同目录重建只修改 A 专属入口、脚本或样式。 | B 的采用包可逐字回看，B 无新增人工确认。最新预览可读，能看清采用版和最新版。 |
| 共享表单的一条校验同时被 A、B 的验收采用，另有一份纯参考该资料的 C。 | 工作台能定位 A、B 被影响的校验和验收。C 的确认仍有效，人工确认数为 0。一次来源变更在各份 Spec 中最多出现一次对应提醒。 |
| 共享资料变化但影响未知，或文件临时不可读。 | 未知影响按 Q2 处理，可见基线与差异原因。来源异常可定位。旧版记录可查，当前确认按实际可读材料校验。 |
| 撤回本轮改动，恢复到已确认的范围与材料。另测原延期刚到期。 | 材料和条件都与历史确认一致时复用原确认 ID。延期到期时原题显示复查原因，历史仍可引用，当前确认遵循题目的适用范围。 |
| 已交付的 B 修改自己的姓名长度规则，分别演练草稿、就绪、明确启动和通过交付。 | 按 Q1 展示完成与当前工作，保留上一轮真实交付。新目标确认只绑定新版实际范围和证据。 |
| 单改无关工程文件、改实际依赖文件、更换联调或部署版本。 | 无关文件改动且范围可证实时沿用原证据。实际依赖影响只提示相应阶段。联调和环境报告显示原验证组合，新组合得到独立核实。 |
| 用旧库重放真实截图状态及仅有摘要的旧记录。 | 历史相同 ID、快照和确认数可核对。联系人、加载、患者按各自证据展示已交付事实，主规格继续显示实际验证和交付缺口。快照不足时说明未知。升级、重复刷新和重新打开结果一致。 |
| 打开 B 的确认后，分别并发修改 A 的无关材料和 B 的确认材料。 | 前者仍能以同一候选完成 B 的确认，后者提示版本冲突并保留输入。CLI、列表、看板、详情的结果一致。 |
